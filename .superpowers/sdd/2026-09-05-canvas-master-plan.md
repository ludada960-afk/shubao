## 0. 一句话愿景

用户上传任意素材（图/文/视频/音频），通过"选中 → 端口 + → 拖线 → 派生"的方式串联成
**图 → 文 → 视频 → 音频** 的完整工作流，最终一条链产出可直接投放的电商内容。

对标：Quantv（laoyu.quantv.com）的画布交互 + B站视频《电商无限画布工作流》的派生串联。
**绝对原则：所有生成类动作只有一个入口 = 选中素材 → 素材右侧 + → 派生菜单。**
任何地方再出现并列的"生成xx"按钮就是重复，先来这里查再动手。

## 5. 方法论（怎么做这些事）

1. **每个交互改动 = 4 步闭环**：读本文档确认不重复 → 改代码 → 更新契约测试 → 真浏览器验证（`npx vite --port 5199` + Chrome 开 /ec-canvas，部署前必须过）。
2. **新增派生动作 SOP**：登记 §3.1 矩阵 → canvasActionRegistry 加 action → CANVAS_CREATION_OPTIONS 加 option（带 gating）→ 派生执行链（P0-1 模式）→ 契约测试 → 部署验证。
3. **绝不新增并列生成按钮**。发现重复入口 = 先删后改。
4. **TDZ 防范**：index.jsx 里 useCallback 互相引用必须先声明被引用者；每次动 index.jsx 后跑 dev server 看一次整页。
5. **部署 SOP**（已验证可照抄）：`npm test`（2906 全绿）→ `npm run build` → `tar -czf` dist → scp 到 /tmp → 跑 `.tmp-deploy-remote2.sh`（备份→原子换 assets→cp 顶层→pm2 restart）→ curl 校验 bundle hash。
6. **推送 SOP**：`git -c http.proxy=http://127.0.0.1:7993 push origin codex/ecommerce-stability`（直连被墙；代理挂了就等，别把 tar.gz 提交进 git——.gitignore 已防）。

## 9. 市场化账号体系（9-05 用户新需求，已排入 P1.5，设计定稿如下）

### 9.1 登录/注册页重设计（参考灵图AI + 椒图AI 截图，用户已提供）

结构（登录/注册双 Tab + 手机/邮箱双通道）：
- Tab1 登录：手机号(+86 前缀) / 邮箱 二选一 + 验证码（获取验证码倒计时 60s）+ 邀请码（选填，注册时生效）
- Tab2 注册：同通道 + 设置密码/确认密码（可选，验证码登录为主流可省密码）+ 协议勾选框（未勾选时注册按钮禁用并提示）
- 底部固定：「登录即代表同意《用户协议》和《隐私政策》」链接 → /terms /privacy 两个静态页
- 视觉：暖米底延续全站；渐变头部带 IP 吉祥物（椒图式）；输入框 48px 高、内嵌图标；主按钮黑底圆角
- 邀请位预留：注册 Tab 邀请码输入框常驻（功能未上前隐藏/置灰都行，接口字段先留）

后端改造点：
- auth_users 增加 phone 列（唯一索引）+ send-code 支持 sms 通道（供应商接口留桩：`server/auth/smsProvider.mjs`，备案前 mock，备案后填阿里云/腾讯云 SMS 即可）

### 9.2 隐私政策 / 用户协议（上线前置项，ICP 备案必需）

- 生成后必须由用户/法务过目一遍再上线

### 9.3 邀请码 + 兑换卡机制（管理后台先行，市场化建议）

**邀请机制（增长飞轮）建议采用"双边奖励"**：
- 邀请人：被邀请人完成注册并首次充值后，得首充金额 20% 等值积分（封顶 500）
- 被邀请人：注册即得 10 积分体验金（仅限首次）
- 反滥用：同设备/同支付账号视为同一人；邀请码每账号 1 个、可重置；奖励积分标记 expires_at=30天（复用现有 expiry-first 扣费顺序，先消耗后过期，运营成本可控）
- 数据表：invite_codes(code, owner_email, created_at, revoked) / invite_rewards(invitee, inviter, status[pending_frist_pay→granted], units, granted_at)
- 管理后台：邀请码列表（搜索/封禁/手动补发奖励）+ 数据看板（注册转化率、K 因子）

**兑换卡（实体卡/电商卡密）建议**：
- 卡密格式：SHB-XXXX-XXXX-XXXX（32 位随机，服务器存哈希）
- 面额：与永久积分包同价体系（30/105/295/760 积分对应 9.9/29/79/199），线下渠道加价 10-15% 由渠道商赚
- 兑换入口：定价弹窗顶部"卡密兑换"链接 → 输入卡密 → 积分立即入账（grantUnits, 无 expiry）
- 防刷：单账号每日兑换上限 5 次；同 IP 限频
- 数据表：redeem_cards(code_hash, units, batch_id, status[unused/used/revoked], used_by, used_at, channel) + batches(渠道批次，区分京东/淘宝/线下经销商)
- 管理后台：批次生成（指定面额×数量）、导出卡密 CSV（发货用）、核销状态查询、作废

## 10. 2026-09-06 P0 构建卡点结案（重要方法论，后续会话必读）

**结论："vite 产物不含源码新改动"是验证方法错误，构建/产物/线上从未丢失任何修复，无需重新部署。**

- EcCanvas 是 React.lazy 动态导入 → 编译进**独立懒加载 chunk** `dist/assets/index-BrfQVtFR.js`（396KB）；`index.html` 引用的 `index-DyUHUGIF.js` 只是主入口（App 外壳），本来就不含画布代码。前几轮 grep 主 bundle 找画布字符串 → 误判"产物是极旧版本"。
- "BUILD OK 但 hash 不变" = 确定性构建（同源码 → 同内容 hash），不是缓存病、不是 dist 残留。

### 验证产物三原则
1. 页面级代码对准**懒加载 chunk** 验证，先确认目标模块被编译进哪个文件再 grep。
2. 线上产物对比必须用 node fetch + Buffer 长度 + sha256（本机 curl 对大文件会偶发截断，曾给出 379235B 假大小引发"同名不同大小"假矛盾）。
3. marker 法用真实 UI 字符串（新建文本/6400），`//` 注释会被生产构建剥离，必然"找不到"。
