## 1. 流程闭环分析 (三步 + 修改传递)

### 1.1 三步定义 (画布工作台 EcCanvas 视角)

第 1 步 (视觉反推):
- 入口: 用户上传商品图 -> 触发电商套图 composer 节点
- API: 内部 /api/generate-ecommerce -> orchestrator.executeJob
- 调用: analyzeVisualInputs(payload) -> visualAnalysisService.analyze
- 模型: gpt-5.6-luna (MINI_MODEL)
- 输出: productTruth + styleReferenceProfile
- 计费: 0 次 (orchestrator 不为反推创建 hold)
- 持久化: visualInputSnapshot + orchestrationSnapshot

第 2 步 (设计方案生成):
- 入口: composer suiteStep === 'generate-suite' (未达 directions)
- API: /api/ecommerce/design-directions (POST)
- 模型: gpt-5.6-luna (createEcommerceVlmClient -> completeText)
- 内部两阶段:
  - stage='vision': 有界视觉观察 -> analysis
  - stage='planner': 文本规划 4 套 direction
- 计费: 0 次 (默认 refresh !== true, 主流程不走 canvasOneShotBilling)
- 仅有手动 refresh=true 才扣 1 次 (ec_direction_refresh, 1000 单位)

用户修改 (关键桥梁):
- 前端编辑器: EcommerceDesignPlanEditor (L88-139)
  - '统一视觉基线' section (L106-124): 6 项生成规格 + 核心叙事
  - '逐张规划' section (L125-137): 每张图 8 字段
- 关键函数:
  - updateCanvasSuitePlanField (L276-279): 修改基线字段
  - updateCanvasSuitePlanShot (L281-295): 修改单张图字段
  - applyCanvasSuitePlanToDirection (L310-360): plan -> direction

第 3 步 (生图):
- 入口: composer.suiteStep === 'directions' -> generateEcommerceSuite
- API: /api/generate-ecommerce (POST)
- 服务端: orchestrator.executeJob (再次执行, 复用 snapshot)
  - 从 snapshot 取出 productTruth + styleReferenceProfile + campaignBible
  - billing.hold (创建 N 单位 hold, 单 SKU)
  - assetPlan 循环, 每次:
    - compileAssetRequest -> providerAdapter.submitEdit (中转 image2/nano)
    - polling -> downloading -> quality_check -> settle
- 模型: gpt-image-2 (默认) 或 nano-banana-2
- 计费: 1 次 hold + N 次 settle = 用户总共扣除 N 单位

### 1.2 信息闭环验证

信息从第一步到第三步是否丢失/混乱? 答: 没有丢失。闭环通路是:

第一步 payload (商品图 + 提示词)
  -> visualInputSnapshot (规范化资产)
  -> analyzeVisualInputs (gpt-5.6-luna 反推) -> productTruth + styleReferenceProfile
  -> buildAssetPlan -> assetPlan (含 role/label/purpose/creativeExecution/variationKey)
  -> orchestrationSnapshot (持久化)
  -> billing.hold (单 SKU, 单价 × assetPlan.length)

第三步 payload (direction.editableBrief + 用户修改)
  -> compileCampaignBible(direction, overrides.editableBrief, styleReferenceProfile)
    -> campaignBible.editableBrief = 用户修改的文字版本
  -> compileAssetRequest(item, productTruth, campaignBible, ...)
    -> generationInstructions.composition = campaign.composition (含 editableBrief)
    -> generationInstructions.palette = campaign.palette
    -> generationInstructions.campaignBible = campaignBible 整段
  -> prompt 注入到 gpt-image-2 / nano-banana

两个关键路径验证:

1. 第二步的 designDirection 通过 direction 字段传到第三步:
   - 前端 L1082 把 direction 写进 body

   - 然后 compileCampaignBible(direction, campaignOverrides(payload, direction, inputAssets))
   - campaignOverrides (orchestrator.mjs:522-540) 用 direction.editableBrief || direction.execution_guide || direction.description || direction.brief || '' 作 editableBrief override
   - 用户在前端修改的 plan.brief -> applyCanvasSuitePlanToDirection -> direction.brief / direction.execution_guide -> editableBrief -> campaignBible.editableBrief -> 注入 prompt。链路是通的。

2. 逐张图修改 (plan.shots):
   - 用户在 EcommerceDesignPlanEditor 里展开单张图, 修改 8 字段
   - updateCanvasSuitePlanShot -> plan.shots[i].{objective, visualStyle, scene, productFocus, composition, contentElements, copy, negativeConstraints}
   - applyCanvasSuitePlanToDirection (L310-360) 把 plan.shots 写回 direction.deliverables[].shots[].generationSpecification (L324-333), 编译为 design_goal / visual_style / scene / product_focus / composition / content_elements / copy / negative_constraints

## 3. gpt-5.6 必要性分析

### 3.1 gpt-5.6 当前承担的职责

关键证据: index.mjs:1047 `MINI_MODEL = process.env.MINI_MODEL || 'gpt-5.6-luna'`

gpt-5.6-luna 通过 createEcommerceVlmClient (L3771-3780) 同时担任 5 个角色:

| 角色 | 调用点 | 必填? | 替代方案 |
|------|-------|-------|---------|
| 1. 反推 productTruth | visualAnalysisService.analyze -> callVision (L308-323) | 是 | nano 没有结构化 JSON 输出能力, 不可用 |
| 2. 反推 styleReferenceProfile | 同上 style 阶段 | 是 | 同上 |
| 3. 设计方向 vision 阶段 | designDirectionService.generate -> completeText stage='vision' (L431) | 是 | 必须有结构化 analysis |
| 4. 设计方向 planner 阶段 | designDirectionService.generate -> completeText stage='planner' (L487) | 是 | 必须能输出 4 套 direction JSON |
| 5. 文案润色 + auto-recognize | callMiniLLM 多处 | 是 | 小调用, 但同样需要 JSON 解析能力 |

### 3.2 生图模型能否取代?

答: 不能。生图模型 (gpt-image-2 / nano-banana) 是像素生成模型, 不是大语言模型。它们:
- 不能输出结构化 JSON (productTruth, styleProfile, direction plan)
- 不能可靠抽取事实 (颜色, 材质, 组件, 文字)
- 不能做创造性规划 (4 套方向)
- 不能文生文 (润色)

gpt-5.6 的不可替代性:
- 业务关键链路 = 反推事实 → 规划结构 → 生图。事实抽取和规划必须用语言模型
- 即使 nano-banana (Gemini) 是多模态, 它擅长生成图像, 但用 prompt 让它输出结构化 JSON 用于下游编辑 prompt, 质量比纯 LLM 差很多 (RTK.md 已记录 8/26 演练发现 PLANNER_TIMEOUT 高频)
- catalog 现状: 反推/规划调用 **不计费** (0 元用户成本, 0 元 providerCost), 完全白送。这意味着**只要中转站 LLM token 不贵, gpt-5.6 的存在 = 净利润**

### 3.3 利润率影响 (假设取消 gpt-5.6)

| 取消项 | 用户感知 | 利润影响 |
|--------|---------|---------|
| 取消反推 (用占位 productTruth) | 生图模型不知道商品事实, 出图变差, 用户拒绝付费 | -100% |
| 取消设计方向 (直接生图) | 一次生图 = 6 张全失败概率↑, 重试率↑ | -30%~50% |
| 仅用生图模型自身规划 | 不可能 (见 §3.2) | 不可行 |

结论: gpt-5.6 是电商生图流程的**事实和规划基础**, 不存在替代品, 而且因为不计费, 它是**净利润来源**。

答: 正面影响。理由:
- 当前用户看完 6 项基线 + 6 张图 × 8 字段 = 54 个 textarea, 信息过载, 修改成本高
- 删基线后用户聚焦 6 × 8 = 48 字段, 全部是图片级 (直接关联要生成的图)

## 5. 综合结论与建议

### 5.1 回答用户 4 个疑问 (精炼)

1. **流程自洽**: 自洽。第一步反推结果 (productTruth + styleReferenceProfile) 通过 orchestrationSnapshot 持久化, 第三步从 snapshot 取出 + 用户修改 (direction.editableBrief + plan.shots[i].generationSpecification) 编译到 campaignBible + compileAssetRequest.generationInstructions, 注入生图模型 prompt。链路完整, 无信息丢失。

2. **扣费次数 (画布工作台主流程)**: 
   - 反推: 0 元 (gpt-5.6-luna 调中转站不计费)
   - 设计方向: 0 元 (同样 gpt-5.6-luna, 即使两次 stage 也不扣)
   - 生图: N 元 (N = assetPlan 长度, ec_image_2k 1000 单位/张, ec_nano_flash_2k 1500 单位/张)
   - 总计: 用户花 N 元, 中转成本 0.038~0.06 × N 元 + ~0.02 元 LLM token

3. **gpt-5.6 必要性**: 必要。它是反推+规划的语言基础, 生图模型不能替代 (不能输出结构化 JSON), 而且不计费 = 净利润来源。

4. **用户方案 (保留逐张规划, 删统一视觉基线)**: 完全可行, 推荐实施。信息链路不断, 用户体验提升 (从 54 字段降到 48 字段 + 简化事实摘要), 不影响计费。

### 5.2 实施优先级建议

| 优先级 | 动作 | 预计工作量 |
|--------|------|----------|
| P0 | 实施用户方案 (删统一视觉基线, 保留逐张规划+事实摘要) | 1 文件 ~50 行删除, 加 CSS 清理 |
| P1 | 在 EcCanvas 设计方向按钮上加 默认不扣费 提示 (提高透明度) | 1 文件 ~20 行 |
| P2 | 把反推 + 设计方向 LLM 调用接入 usage_events 但 providerCostCny=0 (数据完整性, 不扣费) | 1 文件 ~10 行 |
| P3 | 监控 PLANNER_TIMEOUT 频率, 必要时切到 gpt-5.6-mini 减少 timeout | 观察为主 |

### 5.3 利润率影响

当前状态:
- 用户付 N 元, 中转成本 ~0.04 × N 元 (生图) + ~0.02 元 (LLM, 摊薄可忽略)
- 单张毛利 >95%

实施用户方案后:
- 计费链路不变 -> 利润不变
- 用户体验改善 -> 转化率可能↑, 间接利润↑

取消 gpt-5.6 (假设):
- 反推变差 -> 生图成功率↓ -> 用户拒绝付费
- 设计方向变差 -> 6 张图可能全失败 -> 重试率↑ × 每次仍扣费
- 净利润负, 不可行
