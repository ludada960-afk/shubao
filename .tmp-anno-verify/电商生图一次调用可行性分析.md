## 1. 生图模型技术能力边界

### 1.1 三种生图端点的能力对比

| 端点 | OpenAI gpt-image-2 | 中转 65535 gpt-image-2 | Change2Pro nano-banana |
|------|-------------------|------------------------|------------------------|
| API path | /v1/images/edits (主) + /v1/images/generations (备) | 同 OpenAI (中转透传) | Gemini native: generateContent w/ responseModalities: TEXT,IMAGE |
| 输入 | images[] + prompt + size + model | 同 OpenAI | parts: inlineData[] + text |
| 输出 | 单张 PNG/URL | 单张 PNG/URL | 单张 PNG + 文本(可选) |
| 一次多图 (n>1) | 不支持 (官方 docs 仅 dall-e-3 标记 n, gpt-image 系列已废弃) | 同 OpenAI | Gemini 不支持 (imageConfig 只有 aspectRatio + imageSize) |
| 结构化 JSON 输出 | 不能 (endpoint 强制返回 image) | 同 | 不能 (image bytes only, text 流不可靠) |
| 视觉事实抽取 | 不能 (无 OCR/分类 head) | 同 | 部分 (Gemini 可同时返回 text 描述, 但不可靠, 不是结构化字段抽取) |
| 多方案规划 | 不能 (单图生成, 无 sequence 输出) | 同 | 不能 |
| 文案润色 | 不能 (只能 text-in-image, 不能 text-out) | 同 | 不能 |
| 实时调用单价 (薯包 catalog 2026-08-26) | ec_image_2k 0.038 元/张 (1 积分) | 同 | ec_nano_flash_2k 0.06 元/张 (1.5 积分) |

### 1.2 代码层强制单图

证据 1 — providerAdapter.mjs:249-285 buildNativeTask 在 native-tasks 协议体里硬编码 n:1:

```js
return {
  body: JSON.stringify({
    kind: image,
    model,
    input: {
      prompt,
      ...nativeSizing,
      n: 1,  // 硬编码
      ...(images.length ? { image: images.length === 1 ? images[0] : images } : {}),
    },
  }),
  idempotencyKey,
};
```

证据 2 — submitEdit 永远只产生 1 个 jobId: providerAdapter.mjs:364-423 接收 1 个 prompt + N 张 input image, 但返回 { jobId, status } 单 job, 中转站返回 extractOutputUrl 同样只取 result_urls[0] (providerAdapter.mjs:144-156), 即使 API 真返回多张 URL, 代码也只取第一张.

证据 3 — nano-banana 单图: nanoBananaProviderAdapter.mjs:184-211 submitEdit 调用 Gemini generateContent with responseModalities: TEXT,IMAGE, Gemini imageConfig 只支持 aspectRatio + imageSize, 没有 candidateCount / 多图参数. outputImage(payload) 只解析 first image, 返回单张.

证据 4 — gpt-image-2-n 是死代码: modelCatalog.mjs:72-86 selectGenerationModel 输出字符串 gpt-image-2-n 当 eligibleBatch 满足 (assetCount 2-4 + sameStyle + 高风险=false + 无 4K 强制), 但 providerAdapter.submitEdit 不识别这个 model name, 实际永远走单图. promptCompiler.mjs:594-596 硬编码 assetCount: 1, batchEligible: false, sameStyle: false — 即批量分支永远走不到.

证据 5 — OpenAI 官方 docs: 在 platform.openai.com/docs/guides/images 抓到的 760K 字节内容里, 反复出现的是 token 计量 (A 1024 × 1024 image needs 32 × 32 = 1024 patches) + image input fidelity 分级 (low/high/original/auto), 没有任何 multiple images in one request / n parameter for gpt-image-2 的描述. DALL-E 系列才有 n 参数; gpt-image-1/2 已统一为单图调用 + 多轮循环.

### 1.3 一次调用出多张变体 在三种生图模型上的真实含义

| 解读 | gpt-image-2 | nano-banana (gemini-2.5-flash-image) | gemini-3-pro-image |
|------|-------------|--------------------------------------|---------------------|
| 同 prompt 一次出 N 张 (n: N) | 不支持 | 不支持 | 不支持 |
| 在 prompt 里写 give me 4 variants 让模型自发生成 4 张 | 偶尔可能但不可控, 大概率仍只出 1 张 | Gemini 多模态可能返回多张 image (但 result 不稳定, 不是契约) | 同 nano-banana |
| 一次提交多个 image + 1 prompt → 1 张输出图 | 支持 (/v1/images/edits 多张 input) | 支持 | 支持 |

结论: 即便 OpenAI/Google 未来开放 n: N 给 gpt-image-2/3 或 nano-banana, 也只是同 prompt 同一构图出 N 张变体 (类似 seed 差异), 不解决反推/规划 5 角色的需求:

- 不能输出 productTruth (颜色/材质/组件/规格的 JSON 字典)
- 不能输出 styleReferenceProfile (光位/构图/色调的 JSON)
- 不能输出 4 套 direction (creative_route + visual_system + deliverables)
- 不能做文案润色 (生成文字 != 润色文字)
- 不能在 4 套方案之间让用户选择 — 用户拿到的只是变体, 不是方案
- 不能让用户修改 整体视觉基线 后让所有图同步更新 — 像素模型无状态, 修改必须再调用一次

## 2. 模式 A vs 模式 B 成本精确对比

### 2.1 模式 A (当前, 推荐保留)

```
第 1 步 反推          gpt-5.6-luna analyzeJson     1 次  (不计费)
第 2 步 设计方向 vision   gpt-5.6-luna completeText    1 次  (不计费)
第 2 步 设计方向 planner gpt-5.6-luna completeText    1 次  (不计费)
第 3 步 生图 (6 张套图)    gpt-image-2 submitEdit ×6  6 次  (6000 单位, 中转 0.038×6=0.228)
─────────────────────────────────────────────────────────────────
合计                                       9 次中转调用
用户扣费: 6000 单位 ≈ 6 元 (单 SKU 2K × 6)
中转成本: 0.228 元 (gpt-image-2) + 0.02 元 (LLM token, 摊薄可忽略)
单套图毛利润: 5.77 / 6 ≈ 96.2%
```

关键证据:

- 反推不计费: visualAnalysisService.mjs:281 调 analyze → vlmClient.createVlmClient().analyzeJson(request) → 内部调中转站 /v1/chat/completions (vlmClient.mjs:179). 整个调用链路没有任何 wallet.hold / canvasOneShotBilling.execute, 因为它不在 catalog 任何 SKU 里 — 0 用户扣费.
- 设计方向不计费: index.mjs:4141 /api/ecommerce/design-directions 默认 refresh !== true, 跳过 canvasOneShotBilling.execute (index.mjs:4146). 两次内部 LLM 调用 (vision + planner) 都是 chat/completions, 不计费.
- 生图 6 次: orchestrator.mjs:2080 billing.hold + 6 次 providerAdapter.submitEdit (orchestrator.mjs:1459), 每次 hold 1 张 = 1000 单位 = 1 元.

### 2.2 模式 B (假设全程纯生图模型)

用户问的理想模式 — 反推+设计方案+6 张图全由生图模型一次调用搞定.

推演: 用户上传 1 张商品图 + 1 张参考图, 调 1 次生图模型, prompt 要求:
反推商品事实 (颜色/材质/规格) → 输出 4 套方案 → 每套方案生成 1 张主图 → 总共输出 4 张图 + 1 段 JSON 描述

结果: 不可行

1. 生图模型不接受这种 prompt: 它只能接受 prompt → image, 不能 prompt → image + text JSON. Gemini 理论上可同时返回 text, 但:
   - text 输出是描述性自然语言, 不是结构化 JSON
   - 即使返回 JSON, 也没有字段校验, 客户端无法可靠解析
   - 没有 response_format / json_schema 约束 (这些是 chat/completions 端点的能力)
2. 即使 nano-banana 一次返回 4 张图 (Gemini 偶尔可能, 不稳定), 用户也无法:
   - 修改整体视觉基线 后让所有图同步更新 (像素模型无设计记忆)
   - 选择 1 套方案而不是 4 张变体
   - 编辑单张图的核心叙事/composition/content_elements字段 (像素模型没有这些结构)
3. 成本比较 (假设可行):

| 方案 | 中转调用次数 | 用户扣费 | 中转成本 |
|------|------------|---------|---------|
| 模式 A (现状) | 9 次 | 6000 单位 (6 元) | 0.228 元 + 0.02 元 LLM |
| 模式 B-1: 生图模型反推+规划+生图 (假设可行) | 1 次 | 6000 单位 (6 元) | 0.038×6=0.228 元 |
| 模式 B-2: 生图模型只反推, 生图仍 6 次 | 9 次 | 6000 单位 (6 元) | 0.228 元 + 0.01 元 |
| 模式 B-3: 完全无结构化步骤, 一次 prompt 6 张图 (有损) | 6 次 | 6000 单位 (6 元) | 0.228 元 |

模式 B 的省在哪里? 没有. 中转成本几乎一样 (0.228 元), 用户扣费一样 (6 元), 只是把 LLM token 成本 0.02 元省了 — 但损失的是结构化规划能力, 这直接决定生图成功率.

### 2.3 假设真能省: gpt-image-2-n 批量模型

modelCatalog.mjs:86 留有 gpt-image-2-n 字符串, 暗示未来可能批量出图. 即使假设实现:

```
模式 C: 1 次 gpt-image-2-n 调中转, 1 张 prompt 出 4 张图 (假设支持)
中转调用: 1 次 (而不是 6 次)
用户扣费: 假设同样 6 张 = 6000 单位 (中转站大概率按张计费, 折扣需要看真实报价)
中转成本: 0.038×6=0.228 元 (打折前一样, 打折后可能 0.04×6=0.24 元 — 反向更贵)
实际收益: 6 次 polling/download 合并成 1 次 = 省 5 次 5~10 秒 polling
```

结论: 即使 gpt-image-2-n 实现, 省的只是 5×5~25 秒等待时间, 不是钱. 而且生图模型必须按张计费 (中转透明), 用户积分也不变.

## 3. gpt-5.6 必要性 — 多视角验证

### 3.1 资深电商卖家视角

问: 我能不能少花钱? 多花 gpt-5.6 这笔 (其实免费) 算什么?

事实:
1. gpt-5.6-luna 调用 3 次, 用户不扣费. 这是产品设计的核心 — 反推和规划是用户的决策辅助, 不是产品交付, 不应二次收费.
2. 卖家视角关心的不是中间调了什么模型, 而是:
   - 能不能修图 (支持, 通过 plan.shots[i].generationSpecification 8 字段编辑)
   - 重生成成本 (单张 1 元, 由产品决定)
   - 退款率 (反推质量差 → 生图失败 → 重生成 → 用户拒绝付费)

结论: gpt-5.6 是白送的产品质量保证. 卖家不会因为有它觉得贵, 反而会因为没它觉得图丑.

### 3.2 资深电商美工视角

问: 没有反推和规划, 我手写 prompt 能搞定吗?

美工真实工作流:
1. 收到商品图 → 识别材质/颜色/形状/文字
2. 收到参考图 → 识别风格/构图/光线
3. 综合判断 → 选 1 个方向 → 写具体 prompt
4. 反复 5~8 轮微调

如果让生图模型自己做步骤 1-3, 输出是变体而非经过推理的方案. 美工拿到的不是决策依据, 是 6 张盲盒. 试错成本远超现状.

结论: 美工依赖反推和规划结果作为决策依据. 砍掉 gpt-5.6 = 砍掉美工的思考工具.

### 3.3 产品经理视角

问: 用户体验会变差吗?

| 维度 | 现状 (模式 A) | 纯生图 (模式 B) |
|------|---------------|------------------|
| 决策时间 | 用户看 4 套方案 → 选 1 套 → 生成 6 张 (5 分钟) | 用户盲等 1 次 → 拿到 6 张变体 → 自己挑 (3 分钟) |
| 决策依据 | 4 套方案都有创意说明 + 视觉规格 | 只有 6 张图, 用户靠眼缘判断 |
| 修改能力 | 改基线/单张 8 字段 → 自动同步到 prompt | 不能改, 只能重生成 |
| 成功率 (用户能拿到可用品的概率) | ~85%+ | ~40~60% (盲盒, 一次出 6 张都不可用的概率 ~20~40%) |
| 重生成成本 | 单张 1 元 | 整套重生成 6 元 |

结论: 纯生图模式把产品决策的责任推给用户, 而用户其实没能力判断 (他们不是美工).

### 3.4 架构师视角

问: 代码改造成本和长期维护成本

| 改动 | 工作量 | 风险 |
|------|--------|------|
| 砍 gpt-5.6, 用生图模型反推 | 极难 (生图模型不支持 JSON, 需重写 visualAnalysisService + designDirectionService + promptCompiler) | 高 (反推质量↓ → 生图成功率↓) |
| 砍设计方向, 直接生图 | 中等 (删 designDirectionService, 改 buildAssetPlan 直接接收 prompt) | 高 (assetPlan 失去方向/可追溯性) |
| 保留 gpt-5.6, 优化成本 | 低 (catalog 加 gpt-5.6 SKU 但 units=0, 用于数据完整性) | 0 |

结论: gpt-5.6 是架构的心脏. 心脏不能换 — 换心脏等于换产品.

### 3.5 财务视角

问: gpt-5.6 中转成本我花了多少?

vlmClient.mjs:127 timeoutMs = 30_000 默认 30 秒. GPT-5.6-luna 单次调用:
- 输入: 1~3 张图 (≤ 1024×1024, low detail) + ~500 token system + ~500 token user
- 输出: ~800 token JSON
- 单次成本估算 (按 65535 中转 gpt-5.6-luna 价格档): 0.005~0.015 元

3 次 LLM 调用 = 0.015~0.045 元/套图. 用户扣 6000 单位 (6 元). LLM 成本占 0.25~0.75%.

财务结论: gpt-5.6 是净利润的 99%+ 来源, 不是成本. 取消 = 取消商业模式.

## 6. 最终建议

### 6.1 给用户 3 问的精炼回答

1. 能不能全程只靠生图模型一次调用?
   不能. 生图模型是像素模型, 不能输出 JSON, 不能做反推/规划/文案, 即使未来 OpenAI/Google 开放 n>1 多图输出, 也只是同 prompt 同一构图出 N 张变体, 不替代反推+设计方向的角色. 强行替代会让生图成功率从 ~85% 跌到 ~40~60%, 用户重生成成本反而上升.

2. 现在模式是不是最精简?
   是的. 反推+规划 3 次 gpt-5.6-luna 调用 = 0 用户扣费 = 0.015~0.045 元中转成本/套图; 生图 6 张 = 6 元; 单套毛利 96.2%. gpt-5.6 实际上是白送的. 想再砍只能砍用户修改逐张方案功能, 这是反人性的 (用户必须能改, 不然没有付费意愿).

3. gpt-5.6 必要性够不够大?
   不是必要性够不够, 是有没有它整个产品就崩. 它是反推事实 (颜色/材质/规格) + 规划结构 (4 套方向) + 文案润色的语言基础, 而且不计费 = 净利润的 99%+ 来源. 取消 gpt-5.6 = 取消商业模式 (生图成功率↓ → 用户拒绝付费 → 负毛利).

## 7. 重要发现 (新证据, 不在 c3da9800 报告中)

1. gpt-image-2-n 是死代码: modelCatalog.mjs:72-86 输出这个字符串, 但 promptCompiler.mjs:594-596 硬编码 assetCount:1/batchEligible:false/sameStyle:false — 批量分支永远走不到. 即使未来想 1 次调出 4 张, 也需要重写 promptCompiler + providerAdapter (去掉 n:1, 接收多张返回).

2. extractOutputUrl 假设单图返回: providerAdapter.mjs:144-156 只取 result_urls[0]. 即使中转站未来支持多图返回 (OpenAI 现有 dall-e-3 支持 n), 薯包代码也只会处理第一张.

3. vlmClient.mjs 强制 JSON 输出机制很关键: 它通过 systemPrompt 描述 schema, 然后 parseJsonContent (vlmClient.mjs:86-105) 用 JSON.parse 强校验, 失败抛 VISUAL_ANALYSIS_INVALID_RESPONSE — 这是生图模型无论如何也做不到的 (生图模型没有 system prompt + JSON parse 端点).

4. OpenAI gpt-image-2 官方文档 (platform.openai.com/docs/guides/images, 760K 抓取) 没有 multiple images per request 描述: 只有 image input fidelity (low/high/original/auto) + image input cost calculator (patch 计量) — 证实 gpt-image 系列不支持 n 参数.

5. catalog 已有 gpt-image-2-eco (0.10 元/4K) 和 gpt-image-2-auto (0.045~0.095 元 按分辨率) 候选通道: upstreamLedger.mjs:112-113 标注候选通道, 当前未接入. 这是未来降本方向, 但仍是按张计费, 不影响模式 A vs B 结论.

6. 现有架构其实已经 一次提交多张输入: providerAdapter.mjs:231-234 image[${index}] 数组 — 但这是多张参考图 → 1 张输出, 不是 1 张输入 → 多张输出. 反推和规划仍必须用 LLM.
