## 六、协作纪律（这个 worktree 是 5–6 条线共用，踩过的坑都在这里）

1. **提交一律 pathspec**：`git commit -m "..." -- <你的文件>`；提交前 `git diff --cached --name-only` 核对；提交后**看完整输出**（并发会撞 index 锁，可能静默失败）。
2. **严禁** `git add -A` / `git commit -a`；**严禁 `git stash`**（曾把别人整批改动抹掉）；不要 `checkout/reset/restore` 别人的文件。
3. 需要「改前/改后」对照时，用**文件级备份**或**从 HEAD 读一份到临时文件**，不要动 git 快照。
4. 报「主干坏了」之前**先重跑一次**——并发写入会造成瞬时中间态（已有一次误报）。
5. **不许为了变绿而放宽/删除断言**；规范被取代时改断言必须**引用决策编号**。

#### ⚠️ 8.7.1 必须记住的读数纪律（本轮最贵的教训）

**症状**：同一个数字连续三轮对不上（我报 3480/11 红、迁移线报 3616/8 红；我报 Home 有 373 处存量、
迁移线报已迁完 0 处）。**根因不是任何一方的代码，是命令跑错了树。**

```
git worktree list
  F:/da/shubao                                       d9204de8 [master]              ← 误用的
  F:/da/shubao/.worktrees/codex-ecommerce-stability  401fcb1c [codex/ecommerce-stability] ← 真身
git rev-list --left-right --count master...codex/ecommerce-stability   →  3   1372
```

→ master 落后 **1372 个提交**，`src/pages/Home` 在 master 上最后 4 笔还是老提交。

**硬规矩（违反一次就要赔三轮）**：
1. 任何 `git status / log / grep / test` 一律在 **`.worktrees/codex-ecommerce-stability`** 下执行；
2. **报数字必须带 `git rev-parse HEAD`**，否则该数字视为无效；
3. 发现"对方读数和我对不上"时，**先对齐 revision，再讨论谁对**——不许直接改代码去迎合一个可疑的读数。

#### 8.7.2 本轮修复：8 个幽灵变量（未定义 `var()` 静默失效）

### 8.8 第 54 轮（2026-09-20）· 间距迁移等价性 P0 —— 85 处静默改观感

`app-shell.css`、`login-dialog.css`、`pricing-modal.css`、`PublicTemplates/index.css`、`LongTaskOverlay.css`、`Home.css`。

#### 为什么它最危险
1. **间距是布局**：差 1px 就可能换行 / 错位 / 卡片高度变化；
2. **没有任何测试会变红** —— 全站没有断言锁间距，`npm test` 3633/3633 全绿的同时布局已经在变；
3. **它看起来像在做好事** —— 是「往设计规范上靠」，所以最难被 review 拦住。
   → 这正是第 53 轮「幽灵变量」那类 bug 的同族：**静默失效 / 静默改变**，构建与测试都不报。

#### ① 一个家族的三次事故：**同一个作用域里定义了两次 → 后者静默胜出**

| # | token / 规则 | 权威值（文档写的） | 实际生效 | 后果 |
|---|---|---|---|---|
| 1 | `--sb-brand-gradient`（`:root` 定义两次） | 紫 → 薰衣草 | 紫 → **粉** | 全站 8 处引用（含**功能按钮**）渲染成粉渐变：**文档与实现对不上**，且违反裁定 2「功能按钮禁止渐变」 |

⚠️ 本段原为 D23 口径，**D23 已废除**。D23 的错在于假设每个 ink 都会落在白底/页底，
从而逼出 4 个「为对称性硬补」的 -strong，**直接违反 D22**（禁止凭对称性补档）。

**现行口径**：只看**它实际压在什么底上**。实测证据（D25）：
`--sb-ink-brand` 的 7 处用例在各自实际底色上 **4.91–5.70:1 全部达标**；
其深色主题值 `#C4B5FD` 在深色面上 **8.68–10.05:1**。**故 brand 不需 -strong**。
**仅 danger 一族保留 -strong**（D22 原判）。

#### ⑦ §17b 全局焦点基线：把「焦点可见」从浏览器默认值手里拿回来

判据（WCAG 2.4.11 / 2.4.13；原则 4.2 Hover≠Focus；D11）：**任何可聚焦元素默认都要有可见焦点环**。

实测前提：332 个可点选择器里只有 **53 个**自己声明了 `:focus-visible`，其余 279 个**全靠 UA 默认环** ——
而 **Safari 对 `<button>` 根本不画焦点环**：同一个按钮，Safari 用户 Tab 过去什么都看不见。

实现：`:where(a[href], button, input, select, textarea, summary, [role=…], [tabindex]:not([tabindex="-1"])):focus-visible`。
**关键在 `:where()` 特异性为 0** —— 组件自写的 `:focus-visible` 与任何 `outline:none` 抑制**照样赢**，
它**只在「本来什么都没有」的地方**生效：纯增量，不可能破坏既有观感。**禁止** `!important`（门禁断言）。
排除 `[tabindex="-1"]`：那是脚本聚焦的**容器**（对话框根/滚动容器），给容器画环是噪音不是可访问性。

门禁 `test/focus-visible-baseline.test.mjs`（5 条）：元素级基线存在 / 无 `!important` / 环宽 2px /
**环色实测三底色 ≥3:1**（白卡 4.23、暖米白页底 3.70、深色面 3.76）/ 检测器自证（类基线不算全局基线）。

⚠️ 同时**修正了指标措辞**：原来报「显式焦点覆盖率 16%」会让人以为是缺陷率 ——
那其实是**自有实现率**（设计一致性指标）；「看不见焦点」的缺陷由 D11 的**不可达焦点 0 处**单独盯。
