# 84 · 视频模型：家族分组、型号合并与「分辨率为什么在生成设置里」

> 2026-09-25 批 BM。起因是用户的一条批注（逐字）：

> 「你这个模型选择……**为什么 seedance 不放到一起呢？mini max 你也没有放到一起**。
> 然后现在视频生成这里的模型……**为什么会有 720P 的特定模型呢？720P 应该在生成设置里面去选的呀**，
> 用户在这里就只负责选相应的模型就可以了，然后参数是在生成设置里面去做的呀。」
>
> 以及同一批里主动给的一个口子：
> 「**还是说你有其他的策略呢？如果你觉得你的方案更合理，那你也可以告诉我这是为什么呢？**」

这篇文档回答"为什么"，并记录这一轮**改了什么、没改什么、以及为什么没改**。

---

## 1. 用户看到的现象（改前实测）

模型下拉按**目录书写顺序**平铺 12 行，于是：

| 顺序 | 行 |
|---|---|
| 1 | Seedance 2.0 Fast |
| 2 | Seedance 2.0 标准 |
| 3 | MiniMax H3 768P |
| 4 | 通义万相 3.0 |
| 5 | 通义万相 3.0 1080P |
| 6 | 可灵 3.0 |
| 7 | 可灵 3.0 Pro |
| 8 | Seedance 2.5 |
| 9 | MiniMax H3 2K |
| 10 | Seedance 2.0 轻量 720P |
| 11 | Seedance 2.0 满参数 720P |
| 12 | Seedance 2.0 Mini |

四个 Seedance 被切成 4 段、两个 MiniMax 中间隔了 5 行；而且**分辨率写进了型号名**
（「轻量 720P」「满参数 720P」「H3 768P」）——看起来就像"720P 是一个模型"。

## 2. 为什么目录里"分辨率 = 一条产品"（钱路的事实）

站内计费 SKU 由**产品 id** 派生：

```
videoFeatureSku({ productId, duration }) → `video_${productId}_${short|long}`
```

于是**一条产品只能对一条价档**。而分辨率的上游成本是不同的（有据可查的两例）：

| 档位 | 上游单价（文档价） | 站内价 |
|---|---|---|
| 通义万相 720p | ¥0.325/秒 | 11 积分/条 |
| 通义万相 1080p | ¥0.455/秒 | 22 积分/条（用户口径「比 720P 高一倍」） |
| 通义万相 480p | ¥0.26/秒 | 同 720P 价（更便宜的同价档，批 AN 直接放行） |

⇒ 1080P 与 2K 必须各占**一条产品 + 两条 SKU**（批 AN 就按这个开的，用户当时批的价）。
反过来说：480P 因为**比 720P 更便宜**，可以直接加进同一条产品的 `resolutions`
（同价提供不会让毛利变差），这就是"同一个产品能有多个分辨率"的那一半。

**这一层本轮一个字都没动**：没有新增收费项、没有改任何扣费金额、SKU 派生规则没变。

## 3. 改的是什么（展示层合并）

```
服务端目录（钱路）          前端展示（这一轮）
─────────────────          ────────────────────────────────
wan_standard  (720p,480p)  ┐
                           ├─→ 一行「通义万相 3.0」 + 清晰度 480P/720P/1080P
wan_1080p     (1080p)      ┘
minimax_h3_768p (720p)     ┐
                           ├─→ 一行「MiniMax H3」   + 清晰度 720P / 2K
minimax_h3_2k   (2k)       ┘
seedance_fast / _standard / sd_js900 / sd_js / _mini / _25  → 六行（本来就是六种不同的档，
                                                               不是同一个型号的分辨率差）
```

- 目录里每条产品新增 `family / familyLabel`（分组）与 `variant / variantLabel`（型号行）；
  `label` **保持原样**（账单标签、后台、报错文案要靠它认档）。
- 前端 `src/pages/VideoStudio/videoModelRows.js`（纯函数）折叠成
  「家族 → 型号行 → 档位产品」，下拉渲染它；「生成设置 → 清晰度」的药丸也来自它，
  **选哪一档就切到那条产品**（报价、时长上限、素材上限跟着变，按钮上的积分实时更新）。
- 门禁：`test/video-model-families-0925.test.mjs` 四条 —— 分组不重复出现、
  型号名里不许有分辨率、产品一条不多一条不少、页面必须消费分组结果。

## 4. "为什么不干脆把分辨率做成请求参数？"（本轮的自我答辩）

技术上能做，代价写在钱路上：

1. **定价口径要重做**：现在"一条产品 = 一条价档 = 一条 SKU"是计费与对账的单锚点。
   若分辨率变成参数，就要把 SKU 从 `video_${id}_${short|long}` 改成
   `video_${id}_${resolution}_${short|long}` —— 影响 **billing/catalog、账单标签、
   后台映射、历史订单解析** 五处，属于"变更收费项的结构"。
2. **上游并不都支持**：分辨率是**通道属性**，不是随便传的参数。
   - `xn-wan3.0` 一条通道就有 480p/720p/1080p（文档价目三档齐全）⇒ 可以放开；
   - Seedance 2.0 的 1080P 是**另一条模型名**（`seedance-2.0-1080p`，批 AN 已建好产品与两条 SKU），
     目前 `public:false` —— **中转余额不足**（预扣 ¥7.67 > 余额），开了就是"点了必失败"（铁律）；
   - MiniMax 主路由的分档是 720p/1440p/2160p（没有 "2K" 这个写法），报文里由
     `MINIMAX_RESOLUTION` 把 `'2k'` 映射成 `'1440p'`；
   - `minimax-h3`（720P 那一条）能不能出 480p —— **没有实测证据，所以本轮不放开**。
3. ⇒ 结论：**展示层合并 + 钱路保持一产品一价档**是当前最省风险的方案；
   要真正做成"分辨率随便传"，得先有逐通道的实测（零成本探针）+ 一次定价口径的确认（用户点头）。

**所以这轮的做法就是**：用户在下拉里只看到"模型"（Seedance 2.0 / 通义万相 3.0 / MiniMax H3 …），
清晰度在「生成设置」里选；而**账目里仍然是原来的那几条产品与价档，一分钱没变**。

## 5. 还没做的（等证据或等指令）

| 事项 | 卡在哪 |
|---|---|
| Seedance 2.0 的 1080P 档 | 中转余额 < 预扣（¥7.67/条）。充值后把 `seedance_1080p` 与两条 SKU 的 `public` 一起翻 true，它就会自动出现在 Seedance 2.0 下面的清晰度里（`variant: 'sd-2.0'` 已经挂好）。 |
| MiniMax H3 加 480P（或 1080P） | 需要逐通道实测（零成本探针：非法时长提交，上游在**生成之前**就拦下）。没证据不放开。 |
| 其他模型加 480P/1080P | 同上：分辨率是通道属性，先实测再说。 |
| 定价页的档位命名（`pricingCatalogModel.js`） | 那里是**账单透明**的口径（「Seedance 2.0 轻量 720P」），与模型名的简化不冲突；未与用户确认前不动。 |

# 84 附录（2026-09-25 批 BO）：**所有可接入通道的分辨率支持审计** —— 回答了"该统一开 480 还是 1080"

> 用户原话（逐字）：
> 「可是按你这样划分的话，有这个 2k 又没有 1080p，而且这个 2k 它好像只有 mini max 有，是吧？
> 那其他的如果都是有个 1080p 那怎么办呢？其实我觉得如果这个 2k 真的只有迷你麦克斯有的话，
> 那你还不如**直接在模型里面加个 Mini max 2k 的版本**。然后我们到底除了 720p 之外是要加 480p 还是
> 1080p 会更好呢？……**他们最大的公约数里面到底是开放 480 好还是 1080 好呢**？720 我认为是没有问题的，
> 但是其他的是怎么样的呢？……**那到底能不能同时全部都拥有 480 以及 720 呢？然后 1080 又是不是都有呢？
> 这些东西你自己难道没有查清楚吗？**」

## 1. 查清了什么（数据源与口径）

上游 `GET https://api-new.ip233.com/api/pricing`（今天从生产机用 `VIDEO_API_KEY` 抓，只读零成本，
`pricing_version=ip233-route-v2`）。**重要事实：上游没有"参数表"字段** —— 每条记录的键只有
`model_name / description / tags / quota_type / model_ratio / model_price / owner_by / completion_ratio /
enable_groups / supported_endpoint_types`，没有任何 `api_doc` / `parameters`。
"支持哪些分辨率"只能从 **description 那句自然语言** + **模型名里自带的分辨率后缀** 逐条核。

## 2. 逐条审计（我们目录里每条产品走的那条路由）

| 产品（我方） | 上游路由 | 上游说明原文（分辨率部分） | 结论 |
|---|---|---|---|
| seedance_fast | `agv-seedance2.0fast` | 未写分辨率 | **无证据** ⇒ 只给 720p |
| seedance_standard | `seedance-2.0` | 「具体时长和参考素材能力以当前接口响应为准」 | **无证据** ⇒ 只给 720p |
| sd_js900 | `sd-2.0-js900` | 「**固定 720p**，仅支持 9 张参考图」 | 明写固定 ⇒ 不能加 |
| sd_js | `sd-2.0-js` | 「**固定 720p**，9 图 / 3 视频 / 3 音频」 | 明写固定 ⇒ 不能加 |
| seedance_25 | `sd-2.5-js2` | 「**固定 720p**，4-30 秒」 | 明写固定 ⇒ 不能加 |
| seedance_mini | `seedance-2.0-mini` | 「**480p / HD 720p**，4–15 秒」 | ✅ 480p+720p（早已双档） |
| minimax_h3_768p | `minimax-h3` | 「Per-second pricing: **480p 0.108, 720p 0.162, 1080p 0.4725**」 | ✅ 480p 已开（比 720p 便宜）；1080p 待定价 |

## 3. 关键发现：Seedance 系列的 480/1080 **不是参数，是另一条模型名**

同一份清单里，Seedance 的分辨率是**按模型名卖的独立条目**（价格差 5~10 倍）：

| 上游模型名 | 单价 |
|---|---|
| `seedance-2.0-480p` | ¥0.585 |
| `sd-2.0-js900`（= 我们的轻量档，720p） | ¥2.08 |
| `seedance-2.0-720p` | ¥1.2675 |
| `seedance-2.0-1080p`（= 我们藏着的那条） | **¥7.67** |
| `sd-full-1080p` | ¥0（另一类计费口径） |

⇒ 对 Seedance，"在同一个模型下加一档分辨率"**在上游根本不存在**：要么换模型名（成本 3~10 倍），
要么什么都别加。这也正是我们目录里 `seedance_1080p` 必须单开一条产品、且卡在余额上的原因。

反过来，真正**一条路由多档参数**的是这几条：`xn-wan3.0`（480/720/1080）、`xn-minimax-h3`（480/720/1440）、
`minimax-h3`（480/720/1080）、`xn-seedance-2.0(-second)`（480/720/1080/1440/2160）、`grok-video(-1.5)`（480/720）。

## 4. 结论（我们的策略）

1. **判据（一句话）**：**同一条上游路由的档位 = 参数（进"清晰度"）；不同路由的档位 = 另一个模型（进模型行）**。
   - 通义万相 3.0：480P/720P/1080P **同路由** ⇒ 合并一行 + 清晰度药丸 ✔
   - MiniMax H3：480P/720P 在 `minimax-h3` 上 ⇒ 药丸；**2K 在 `xn-minimax-h3` 上** ⇒ **独立模型行**（本批按用户指示拆回）✔
2. **"480 还是 1080"的答案 = 480**（当且仅当上游同路由支持，且**不高于** 720p 的价）：
   - 有明文依据支持 480p 的有 3 条（`seedance_mini` / `minimax-h3` / `xn-wan3.0`），**都已经开了**；
   - 明文支持 1080p 的只有 2 条（`minimax-h3`、`xn-wan3.0`），其中万相已开（用户批过"高一倍积分"），
     MiniMax 那条 1080p 成本是 720p 的 **2.9 倍** ⇒ 属定价决定，**等用户给价**；
   - 其余通道上游**明写固定 720p** 或**根本没写** ⇒ 不猜、不加（铁律：不许放"点了必失败"的东西）。
3. **"能不能都同时有 480+720"**：能，但只有上面那 3 条（`seedance_mini` / `wan_standard` / `minimax_h3_768p`）；
   其余按上游能力就是单档。**"1080 是不是都有"：不是** —— Seedance 全线要出 1080p 得换更贵的模型名。

## 5. 没做的事（如实记录）

- 没有对 `seedance-2.0` / `agv-seedance2.0fast` / `kling-*` 这几条**无证据**的路由做"非法参数探针"：
  历史事故（`sd-reference-image-25`）证明"非法参数"不保证被上游拦下，可能**真的建任务花钱** ⇒
  按铁律（不许跑付费生成）不做。要开这几条的 480/1080，需要用户批准一次真实探针或一次真出片对账。
