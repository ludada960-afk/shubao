**结论：48 条里没有一条是"既品牌中性、又偏编辑级静物"的** —— 因为它们本来就是为

（你的判断是对的），而是要**新增**一条专为这条线设计的 skill。

**今天过渡就用 `image.scene`**（`https://shuimg.cn/image-creation?id=image.scene`，在**电商专区**那一组）：

**不一致**，所以你的「修图指令」里必须显式把它压过去（写明"高端编辑级静物、柔光罩打光、统一调色"）。

## 一-b、**用户提示词优先吗？**（用户 2026-09-25 追问，附代码依据）

答：**在图片这条链上，用户写的话是唯一的内容权威 —— 没有任何"产品默认值"能压过它。**
分三层说，每条都有代码出处：

**① 用户填的字就是 prompt 本身。**
`src/skills/skillRun.js` 第 166~169 行注释原文：「文案组装：把用户填的字段填进该 skill 自己的 brief 模板」；
第 330 行 `const brief = buildSkillBrief(skill, values);`，第 335 行 `prompt: brief`。
⇒ 最终下发给引擎的 `prompt` = **skill 的 brief 模板外壳 + 用户填进去的内容**。
用户写的话**天然在主体位置**，skill 模板只是句式外壳。

**② 站内有一条明文的权威性排序（在画布电商线）。**
`src/pages/EcCanvas/canvasPromptAuthority.js` 顶部注释（注明"注释与测试同步钉住"）：
- **第 1 层 · 硬约束（配置面板）＝ 永远最高优先，提示词不能覆盖** ——
  避免出现的元素(negative) / 品牌主色调 / 尺寸·清晰度 / 平台合规；
  冲突处理是「**硬约束胜出，但绝不静默**」：生成前必须显式写出「已按你的约束忽略提示词中的 X」。
- 第 2 层 · 产出结构（套图方案 + SKU 变体）＝ 决定出什么/几张/什么比例。
- **第 3 层 · 内容意图（提示词 + skill）＝ 提示词优先于 skill；skill 只在 prompt 为空时预填** ← 就是这条。
- 第 4 层 · 设计方案（确认后成为唯一事实源）。

**③ 但第 1 层（硬约束）在图片子页面这条链上不存在 —— 这一条要更正我之前的说法。**
我上一轮说过"反面约束已经端到端跑通（面板 → negativePrompt → 服务端 forbidden）"，
**那是电商画布线**（`server/ecommerceEngine/*` 的 `negativeConstraints` → `compileAssetRequest()` → 请求里的 `forbidden`），
**不是图片子页面这条链**。实测：
- `server/index.mjs` 里 `negative` **0 命中** ⇒ 图片走的 `/api/generate` **完全不读负面词**；
- negative 只在**电商引擎**（`server/ecommerceEngine/*`）与**视频**（`server/videoGeneration.mjs` /
  `server/videoPlanCompiler.mjs`，且视频那边注释写着"服务端权威，客户端绕不过"）被消费；
- `src/pages/MediaCreation/index.jsx` 只有一行第 528 行 `negativePrompt: String(job.negativePrompt || …)`，
  是**带出去**，页面上并没有输入它的格。

**⇒ 所以你的推论成立，而且比"过渡"更强：**
在图片这条链上，**你写什么就是什么** —— 你要品牌就写品牌，不要品牌就不写，
**系统不会替你决定，也没有默认值在跟你的提示词抢**。
所谓"默认无品牌"**根本不是产品默认值，是我们自己在输入框里打的字**，
所以它对其他用户**零影响**、也不需要改任何现有页面。

### ⚠️ 但"到底谁优先"这件事，查清后是这样的（用户 2026-09-25 再追问）

**用户问：「skill 内置的优先级是高于我们的提示词吗？用户难道不该优先级更高吗」**

**答：这段代码里根本没有"优先级"这个东西 —— 它是"拼成一段"，不是"谁覆盖谁"。**

`src/skills/skillRun.js` 第 168~178 行的真实实现是**纯字符串替换**：

```js
export function buildSkillBrief(skill, values = {}) {
  const template = text(skill && skill.brief);
  const filled = template.replace(/\{\{(\w+)\}\}/g, (_match, key) => text(values[key]));
  ...
}
```

⇒ **最终 prompt = 模板里那些固定句子 + 你填的内容，拼成同一段文字。**
模板里的话**不是"更高优先级的指令"**，它**就是提示词本身的一部分**。
所以"skill 优先级高于提示词"这个说法**不成立**；但"提示词优先于 skill"在这条链上
也**没有实现** —— 因为两者根本没被当成两个东西来裁决。

**真冲突的时候会发生什么**（例如模板自带"品牌标识与产品细节必须原样保留"、
你写"画面内不出现任何品牌标识"）：**模型同时收到两句互相矛盾的话，由它自己权衡。**
**程序不做裁决，也不告知你。** 这就是为什么上面那张 brief 审计表重要 ——
它让你**在选 skill 时就避开冲突**，而不是指望系统替你压过去。

**而站内其实已经有正确答案，只是没铺到图片这条线**：
`canvasPromptAuthority.js` 第 3 层明文写着「**提示词优先于 skill；skill 只在 prompt 为空时预填**」，
第 1 层还规定了"硬约束永远最高优先，且**冲突时绝不静默**（必须显式告知）"。
**但这套治理只挂在画布线** —— 实测引用它的只有 `src/pages/EcCanvas/*` 与
`src/pages/Home/ec/PromptAuthorityNote.jsx` + 两个测试，**图片子页面一处都没引用**。

### ⇒ 这暴露了一个**影响所有用户**的真实缺陷（不只是我们）

图片这条线缺三件，每条都有代码依据：

| # | 缺什么 | 证据 | 后果 |
|---|---|---|---|
| 1 | **用户看不到最终下发的完整提示词** | 全仓没有"提示词预览"实现（查过 `提示词预览` / `promptPreview`，0 命中） | 模板自带的话用户**看不见**，冲突只能"盲撞" |
| 2 | **冲突时没有任何告知** | `MediaCreation/index.jsx` 里 `setNotice` 有几十处，但**没有一处**是关于"提示词与 skill 冲突/已按你的来忽略模板" | 画布线有"绝不静默"，图片线静默 |
| 3 | **没有硬约束层** | `server/index.mjs` 的 `/api/generate` 里 `negative` **0 命中** | 负面词/品牌主色这类"硬约束"在图片线**不生效** |

**这不是"我们的私有需求"，是任何一个认真写提示词的用户都会被坑的缺陷** ——
他写了很完整的要求，却被模板自带的反向句子悄悄搅浑，而且**看不见、不知道、也没法申诉**。

**最小修法（三件都很小，且方向是仓库已有的原则）**：
① 把最终提示词**摊开给用户看**（复用画布线的做法与 `PromptAuthorityNote` 的形态）；
② 冲突时**显式提示**（`canvasPromptAuthority.js` 里的 `isStructuralIntent()` 等**是纯函数**，可直接复用）；
③ 图片线**补上硬约束层**（让 `/api/generate` 消费 negative）。
**这三件做完，"用户优先"才是真的优先，而不是靠"你写的话恰好在 prompt 里"。**


**那今天怎么办**：既然程序不裁决、也不告知，就**靠选 skill 时避开冲突** ——
例如 `brand_kv` 自带"品牌标识必须原样保留"、`float_kv` 自带"包装文字必须完整保留"、
`mono_pastel_ad` 自带"品牌标位"，这些就**别用来跑无品牌线**（见上一节的推荐与审计表）。
