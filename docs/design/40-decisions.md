# 40 · 已拍板的设计决策（总统筹·唯一口径）

> 本文件记录**已定死、不再讨论**的决策。任何改造 agent 若与本文冲突，以本文为准。
> 最后更新：2026-09-15

## D1 · 主色 = 品牌紫（不是近黑）
- **决策**：全站主色为品牌紫 `--sb-brand-600: #7C3AED`；近黑**降级为中性强调**，只用于确实需要强对比的场合。
- **依据**：实测硬编码紫 **293 处 / 28 文件**，而 `var(--accent)`（近黑）仅 59 处；画布链路 100% 用紫；首页电商配置链路（EcMode + ec/ 六面板 + DesignDirection）也全是紫。近黑真正只统治 Pricing / Navbar / Works 三处。
- **代价与做法**：不直接改 V2 的 `--accent` 指向（避免全站一次性变色），改为**新增 V3 token + 分批迁移**（见 D5 顺序）。
- **禁止**：再新增任何未经 token 定义的紫色；品牌渐变只用于品牌时刻（logo/hero/空态），**禁止用于功能按钮**。


### D1 · 补充裁定（2026-09-15 第二轮）：品牌红是「标识色」，紫仍是「交互主色」
**新证据（像素级实测）**：品牌资产里**没有紫色**——`public/images/LOGO.png` 主色 **`#F04048` 红占 72.4%**，吉祥物主色 **`#FB5358` 占 62.5%**；全 `public/images/` 仅 3 张图含紫色，共 4.55%，且都是 AI 生成的电商样图、不是品牌资产。也就是说：**品牌红有唯一真源，紫是零资产支撑的外来色**（却已落 215 处代码：画布 116 / 首页 99 / 其他 42）。

**裁定：D1 不推翻——交互主色仍为品牌紫 `--sb-brand-600`；品牌红 `#FB5358` 定位为「品牌标识色」，只用于品牌时刻**（logo / 吉祥物 / hero / 空态插画 / 营销物料）。

**为什么不让红接管交互主色（三条理由，按权重）**：
1) **语义冲突成本高于收益**：红已是全站「危险/删除/折扣」语义色；把「生成」这类主 CTA 改成实底大红，会与删除/报错抢注意力。行业先例（YouTube/Pinterest/Adobe）能用红做品牌，是因为它们没有把红同时当危险色用在同一屏。
2) **用户从未抱怨紫色**：用户抱怨的是「黑白极简、没有主次、没有状态反馈、格格不入」。紫是**已安装的既成事实**（215 处），把它推倒重来属于**未被要求的重大改动**，风险与工期都不划算。
3) **规范自己的权重表说品牌色只占设计感 5%**（表面分层 40% / 排版 25% / elevation 20% / 状态 10%）：**hue 之争是低杠杆问题**，真正让界面变好看的是表面分层与状态。

**「格格不入」的技术原因仍然成立且必须治**：品牌红（色相 ~358°，暖）与页面底 `#F5EFE4`（~35°，暖）同属暖域，而紫（~262°，冷）是跨域色。**处理办法不是换掉紫，而是限定紫的使用面积与位置**（按 §2A 穷举清单：只用于主 CTA / 选中 / focus / 激活图标 / 关键数字），大面积仍是暖白 surface + 中性文字。

**保留低成本切换通道（token 化的红利）**：若老板日后要求「以品牌红为主色」，**只需替换 9 个 `--sb-brand-*` 值**（`50/200/400/500/600/700` + ring + ink），其余规范、组件、状态表全部不动。这就是 token 化的意义——**决策可逆，且可逆成本是分钟级**。
## D2 · 选中态统一用「ring」，不靠加粗边框
- **决策**：选中/聚焦统一用 **token `--sb-shadow-ring`**（其实际值为 `0 0 0 3px var(--sb-brand-ring)`），**不改变边框宽度**，从而**没有布局抖动**。
  - ⚠️ 口径订正（2026-09-15）：本条原文写的是「2px `--sb-brand-500`」，与 token 实际值（3px / `--sb-brand-ring` 32% alpha）不一致。**以 token 文件为准**——规范引用 token 名，**不要在文档里写死像素值**，否则规范与实现必然漂移（这正是我们一直在治的病）。
  - 另一支 `--sb-focus-ring-w: 2px` 服务于 `.sb-focusable` 的键盘焦点环，两者用途不同，不要互相替换。
- **配套三件套**（选中行/卡片）：底 `--sb-state-selected-bg` + 描边 `--sb-state-selected-line` + 文字/图标 `--sb-state-selected-ink`。
- **差异化硬要求**：hover 只做底色变化（`--sb-state-hover-bg`）；**hover 与 selected 必须视觉不同**——这是用户明确要求过三次的点。
- **现状问题**：选中态全站**4 种并存**（紫描边 / 近黑反色 / 靛蓝浅底 / 灰底白 pill），统一到本决策。

## D3 · 靛蓝 Indigo 判定为历史遗留，全部迁往品牌紫
- `#6366F1` / `#4338CA` / `#EEF2FF` 家族（实测 180 处里的 68 处）**不得再用于品牌表达**；如确实需要信息语义色，用 `--sb-info: #5275CC`（已进语义域），不得当品牌色用。

## D4 · 暖黑覆盖层（纯黑 `rgba(0,0,0,α)` 退役）
- 一切覆盖/描边/分隔用**暖黑** `rgba(12,10,9,α)`（与页面底色 `#F5EFE4` 同色相）。
- 纯黑叠在暖白底上会发灰发脏——这是"廉价感"的来源之一。已列入第二批机械替换。

## D5 · 改造顺序（严禁反序）
1. **接 token**（已完成：`src/styles/design-tokens-v3.css`，269 项，已 import，commit `59d1fe82`）
2. **全局暖黑色相替换**（进行中：`rgba(0,0,0,α)` → `rgba(12,10,9,α)`，约 320 处，零布局风险）
3. **surface 分层**（补 35 处分层失败点：未选中态不可见、输入框无凹槽、面板内套白卡）
4. **尺寸统一与主 CTA 组件化**（主 CTA 现测 9 档高度 38–58px → 收敛到 `--sb-control-h-*` 阶梯）
> 反序的代价：先把尺寸改完再替换色相，等于把硬编码重新种一遍。

## D6 · 圆角只有 4 档，10px 退役
- 面板 20 → 内层 12 → 控件 8 → 微件 6（`--sb-radius-2xl/lg/md/sm`）。
- 实测高频的 **10px（62 处）按场景归入 8 或 12**；16px 用于卡片（`--sb-radius-xl`）。
- 嵌套公式：内层 = 外层 − 内边距。



## D10 · 语义色：文字用 `--sb-ink-*`，填充用 `--sb-danger/success/warning`
- 实测：基础语义色直接当文字色时，**在暖米白底上对比度不达标**（danger 4.01 / success 4.43 / warning 4.39，低于 WCAG AA 的 4.5）。暖底会把对比度拉低 0.5–0.9。
- **规则**：① 文字/图标一律用 `--sb-ink-danger` / `--sb-ink-success` / `--sb-ink-warning` / `--sb-ink-info`（已按暖底调深）；② 填充（按钮底、色块底）才用 `--sb-danger` 等；③ 若必须在暖底上用浅色语义文字，必须托一层白卡。
- **验收**：每个语义文字用 WCAG 公式实算对比度并写进测试断言（≥4.5:1）。

## D11 · 键盘可达是硬门槛：focus-visible 必填，禁止裸 outline:none

> **口径修正（2026-09-15，重要）**：本条的判断标准**不是**「有没有出现 `outline:none` 这个字面量」，
> 而是「**抑制默认轮廓的同时，是否给出了可见的替代焦点样式**」。
> 原因：把 `outline: none` 改写成 `outline: 0 solid transparent` **行为完全等效**（照样抑制），
> 只改写法却算作「归零」= **指标被绕过**。真实事故：某批按关键字口径报了「归零」，
> 而按新口径复查发现 **3 处根本没有替代焦点样式**——那是**真的键盘不可访问**，不是口径问题。
>
> **新指标：不可访问焦点点 = 0**（对每处抑制点，检查其 `:focus` / `:focus-visible` 下是否产生
> `box-shadow` / `border-color` / 实描边的可见变化；无 = 真红灯）。审计脚本按此成对判定，不再数关键字。
> **推广到所有指标的原则：指标必须反映行为，不能靠改写量词满足。**
- 实测：全站 `focus-visible` **0 次**（WCAG 2.4.7 AA 违规）、裸 `outline:none` **42 处**、`<div onClick>` **133 处**。
- **规则**：① 所有可交互元素必须有可见焦点态（`--sb-focus-ring`，`box-shadow: 0 0 0 3px`，不改变布局）；② 禁止裸 `outline:none`，必须同时提供替代焦点样式；③ 新写的可点击元素用 `<button>`/`<a>`，不得用 `<div onClick>`；④ 必须尊重 `prefers-reduced-motion`。
- **验收**：每批交付报「本批涉及文件：focus-visible 覆盖数 / 裸 outline:none 剩余数」。

## D12 · 幽灵变量与死代码当 bug 清
- 实测：全站有 **6 个从未定义的 CSS 变量**（`--amber-400` / `--shadow-red-lg` / `--surface-raised` / `--shadow-red` 等）——引用它们的样式**当前渲染为无效值**（静默失效）；`Navbar.jsx`（208 行）是**死代码**（`App.jsx:272` 渲染的是内联 `TopBar`）。
- **规则**：① 新增样式前先确认引用的变量真实存在；② 幽灵变量要么补定义要么删引用；③ 死代码文件确认无引用后删除，并在 commit 说明。
## D8 · 同一个 CSS 选择器只允许一处定义（禁止追加式覆盖）
- **实测现状**：`src/pages/EcCanvas/EcCanvas.css` 2008 行 / 741 选择器 / **60 个重复选择器**（最多重复 6 次）；`src/pages/Home/Home.css` 3551 行 / 930 选择器 / **89 个重复选择器**（最多 6 次）。
- **为什么必须治**：同一个选择器在文件里被反复追加覆盖，等于**每个样式都有多套互相打架的真相**——这正是「改一处坏一处」「同一个控件在不同页面长得不一样」的机制性根因，也是本次审计里 4 档间距 / 8 档高度 / 11 档圆角能长期共存的土壤。
- **规则**：新增或修改样式时，**必须就地改写那一条**，不得在文件末尾再追加一条覆盖。每个批次顺手把该批次涉及文件里的重复选择器合并（保留语义最新的一条，删除被覆盖的死规则）。
- **验收**：每批交付时报告「本批涉及文件的重复选择器数量：改前 → 改后」。

## D9 · hover 位移必须由容器预留空间（三选一，禁止默认被裁）
- **实测现状**：全站 `overflow:hidden` **89 处**、`overflow:auto/scroll` **13 处**，**没有一处为 hover 位移预留空间**；已确认 4 处被裁（`.ec-result-card`、`.ec-preview-ref-strip-item`、**公共 `Card` 组件**（一处受害=全站受害）、`NoteModal` 按钮），另有 11 处潜在风险。
- **规则（三选一，写进组件并注释）**：① 把「位移容器」与「裁切容器」分离（外层管 transform/阴影，内层管 overflow+圆角）；② 滚动容器 `padding:8px; margin:-8px`（≥ 最大位移 + 阴影扩散）；③ 用 `--sb-shadow-*` 的海拔差表达浮起，不做 transform。
- **验收**：首行/首列/末行/末列四个极端位置实测不被裁断。
## D7 · 面板内禁止再套白卡
- 浮层面板（`--sb-surface-panel`，半透明白）内**禁止**直接放 `--sb-surface-card` 纯白卡；分组用**留白 + 分组标题**。
- 依据：白卡叠白面板时两者色差≈0，只剩 1px 描边作分界 → 观感"像一堆小方框拼的表格"，是用户第一眼说"丑"的直接来源。

## D14 · 验收口径：像素对比要「分区段」，有意变更要「单列并给依据」

- **背景**：整屏 `diffPct` 会把**有意的设计变更**算成噪声。实测例：首页模式卡阴影按 token 阶梯归一化后，整屏差异 **5.29% / maxΔ 235**，看起来像严重回归；但**分区段采样显示卡片以外的像素 `d = 0`**（非卡片区完全一致），差异**只来自卡片本身的有意变更**。
- **规则**：
  1. 逐像素验收**必须分区段统计**（至少区分「被改动元素的区域」与「其余区域」）；**其余区域必须 d = 0**，这才是「改动是局部的、无串色」的硬证据；
  2. 每一处**有意的视觉变更**（例如把阶梯外的 `0 16px 34px` 归一到阶梯内的 `0 12px 36px`）必须**单独列出**，并给出依据（哪条决策/哪个 token 档位）；
  3. **不接受**「整屏 diffPct 达标」作为唯一标准——它既可能掩盖真回归，也可能冤枉有意变更。

### D14.1 已确认接受的一处有意变更
`src/pages/Home/Home.css` 模式卡阴影：`0 16px 34px rgba(64,48,36,.14)`（阶梯外硬编码）→ `var(--sb-shadow-lg)`（`0 12px 36px rgba(57,45,26,.13)`，阶梯内）。
- **接受理由**：这是**把阶梯外的值收敛到唯一权威**，正是本次改造的目标；偏移 22px→12px 的观感变化属预期；
- 若日后认为需要更大的浮起感，**应改 `--sb-shadow-lg` 档位本身（一处生效全站）**，而不是在组件里写回硬编码。
## D15 · 迁移只能逐值相等；近似值必须单独裁定（2026-09-20）

- **决策**：任何「字面量 → token」的迁移，**只有与该 token 逐值相等时才允许**。
  近似值（差 1px / 差 1 个色阶）**一律不许机械替换** —— 那是改观感，必须单独裁定并附依据。
- **适用面**：`gap` / `padding` / `margin`（间距）、`font-size`（字号）、`border-radius`（圆角）、颜色，全部适用。
- **加阶梯 ≠ 改观感**：若某个值（如 6px / 10px）出现频率高，正确做法是先由设计裁定**把它加进阶梯**
  （加条目本身零观感变更），再做等值迁移；**不许反过来**「先硬套、再让阶梯去追认」。
- **依据（真实事故）**：第九批以「gap 非阶梯 56% → 0%」为目标，指令里写明「必须给出像素级 diff 证明观感零变化」，
  实际执行成了「非阶梯值硬套最近阶梯」。审计脚本 `scripts/space-migration-audit.mjs` 实测 **85 处**：

  | 位置 | 原值 → token | 实际 | 偏差 |
  |---|---|---|---|
  | `Pricing.css` | `gap: 12px → --sb-space-5` | 20px | **+8px** |
  | `canvas-supervisor.css` / `pricing-modal.css` | `gap: 4px → --sb-space-2` | 8px | **+4px** |
  | `canvas-supervisor.css` ×7 | `gap: 6px → --sb-space-2` | 8px | +2px |
  | `AdminConsole.css` ×4 | `gap: 5px → --sb-space-2` | 8px | +3px |

  **这类回归没有任何测试能抓到**（没有断言锁间距），只能靠等价性审计。
- **工具**：`node scripts/space-migration-audit.mjs`（exit 1 = 有不等价迁移；exit 2 = 脚本内阶梯真值与 token 文件漂移）。
- **为什么这条比单个 bug 重要**：它是**系统性**的 —— 一次错误的迁移口径会在几十个文件上同时改观感，
  而且因为看起来是「往设计规范上靠」，最容易被放过。
- **推论（「剩余量」口径）**：棘轮快照统计的是**全部硬编码**，不等于**映射表内可迁移项**。
  报进度必须把这两个数字**分开写**，否则下一位 agent 会把「不可迁的存量」当成「漏做的活」再踩一次（已坑三轮）。
## D16 · 间距补三个半档（2 / 6 / 10px）—— 治「阶梯在小尺寸段太粗」

- **决策**：间距阶梯补 `--sb-space-0-5: 2px`、`--sb-space-1-5: 6px`、`--sb-space-2-5: 10px`。
- **依据（实测）**：全仓非阶梯 `gap` **645 处 / 14 个值**，分布为
  `6px×154  5px×104  7px×102  10px×79  3px×59  2px×52  9px×34  14px×31 …`。
  排在最前的 **6 / 2 / 10** 恰好是**行业标准半档** —— Tailwind 的 `1.5 / 0.5 / 2.5` 同为 **6 / 2 / 10px**。
  → 结论：不是设计乱，是**主阶梯 4px 起步、小尺寸段太粗**，图标旁的间距只能靠手调。
- **性质**：加档位 = 给已有值一个名字，**零观感变更**（不需要像素 diff），却让 **285 处**可被合法收编。
- **明确不补** `1/3/5/7/9/11/13`：那是 1px 网格上的**手调噪声**，补进去等于把碎片化制度化。
  它们按 **B 类（按场景归并）** 处理 —— 属有意观感变更，必须走 D14 分区段像素 diff。
- **配套**：`docs/design/41-scales-and-snapping.md`（三段阶梯真值 + A/B/C 三类处置政策 + 执行纪律）。
## D17 · 字号补 14px（标准正文）；15px 判为「夹心档」退役（2026-09-20）

- **决策**：
  1. 新增 `--sb-text-base: 14px` = **标准正文**；
  2. `--sb-text-lg: 15px` **退役** —— 按场景归入 14 或 16；
  3. 半像素字号（`11.5 / 12.5 / 10.5 / 13.5px`）归到最近合法档；
  4. `16px` 暂不补档（可由 15px 退役后承接），避免一次撑大阶梯。
- **依据（实测 1474 处声明 / 33 个不同值）**：
  `11px×336  10px×233  12px×227  13px×163  9px×104  14px×78  11.5px×55  15px×49  12.5px×42  10.5px×34  16px×29 …`
- **为什么补 14**：14px 是**行业标准 UI 正文字号**（Tailwind `text-sm` = 14px），全仓已手写 78 处。
  它缺位才逼得各处写死 → 补档是**零观感变更**。
- **为什么退 15**：15px 夹在 14 与 16 之间，**没有任何场景能说明「该用 15 而不是 14 或 16」**。
  它本身就是碎片化的产物。退役是**有意观感变更**，必须走 D14 分区段像素 diff。
- **性质区分（关键）**：补 14px = 零变更；退 15px = 有意变更。**不许把两者混在同一个「零变化」的提交里。**
- 配套：`docs/design/41-scales-and-snapping.md` §1.2 / §2 / §3。

## D20 · 色值裁定：暖棕是「阴影色」、玻璃白是「玻璃色」，都**不是**缺档（2026-09-20）

背景：扫描残留硬编码时，有三族被报为「V3 缺档、需要新增 token」。**复核后三族全部不需要新增** ——
其中两族**本来就是这个体系的组成部分**，只是被按错误的参照物比对了。

### A. `rgba(57,45,26,α)`（38 处）—— **它是 `--sb-shadow-*` 的颜色成分，不是缺档**

实测 `design-tokens-v3.css` §10：`--sb-shadow-1..5` **全部**用 `rgba(57,45,26,·)`，
文件里原文就写着「**暖棕投影 rgba(57,45,26,·) —— 继承现有品牌调性，禁止改用冷灰**」。

→ **不要新增 `--sb-border-warm-*`**；也不要比对 `--sb-border-*`（那是暖黑 `rgba(12,10,9,α)`，
  是**描边/表面**色，不是阴影色 —— 拿它比当然「色相差 20°」，因为**它们本来就是两种用途**）。

正确处置：**按 α 归到海拔档位**：

| 原 α | 目标 |
|---|---|
| ≈0.05 单层 | `--sb-shadow-1`（静态卡片）|
| ≈0.05+0.07 两层 | `--sb-shadow-2`（可点卡片）|
| ≈0.10 | `--sb-shadow-3`（dropdown / popover）|
| ≈0.13 | `--sb-shadow-4`（浮层面板）|
| ≈0.16 | `--sb-shadow-5`（modal）|

**例外**：若 `rgba(57,45,26,α)` 被用作**边框/分隔线**（不是 box-shadow），那确实不属于阴影家族 ——
这类**单独列出报我**，不要混进上面这张表。

### B. `rgba(255,255,255,α)`（61 处）—— **按用途归到已有的玻璃档**

体系里已有：`--sb-shadow-inset-top`（`inset 0 1px 0 rgba(255,255,255,0.90)` = **玻璃面高光**）、
`--sb-glass-panel / --sb-glass-bar / --sb-glass-nav`（§11 毛玻璃白名单的三种合法用法）。

→ **不要新增 `--sb-glass-ring` / `--sb-glass-fill-*` / `--sb-ink-on-glass`**：
  - 高光 → `--sb-shadow-inset-top`；
  - 玻璃面底 → 按角色选 `--sb-glass-panel` / `-bar` / `-nav`；
  - **不在 §11 白名单里的**（普通卡片 / 列表项 / 按钮上的半透明白）→ 按 §11 **改实底**，不是找 token。

### C. 第二支品牌紫（`#7258d6` 等，ΔE 19.9–30.0）—— **不新增 `--sb-brand-550`**

依 **D1**（交互主色只有一个）+ 本文件 §④ 的判据「**按用途分档，不按页面分档**」：
品牌紫再补档 = 同一用途（交互主色）的第二三支 = 把碎片化制度化，与 D16 拒补 5/7/9px 同一把尺。
→ 归并到 `--sb-brand-600` / `--sb-brand-700`。

### D. 口径：**带 alpha 的颜色必须「合成到实际底色后」再算 ΔE**

144 个值 / 204 处无法用纯 RGB 比对 —— `rgba(255,255,255,α)` 在白底几乎不可见、在暗底是主要视觉元素，
**同一个值的观感取决于背后是什么**。纯 RGB 比出来的 ΔE≈93 是**失真**，不是「颜色真的差 93」。

→ **采纳「合成底色后再算」的口径**。所有 alpha 值在迁移前必须先确定它的实际底色。

### 一句话总结
> 遇到「V3 缺这一档」时，先问三件事：**它是不是已有 token 的颜色成分？它属于哪个用途？它的实际底色是什么？**
> 三问之后再谈新增 —— 本次三族全部在前两问就被否掉了。
## D21 · 暖棕「描边用途」归到暖黑描边档（2026-09-20）

**背景**：D20-A 把 `rgba(57,45,26,α)` 的**阴影用途**归到了 `--sb-shadow-*`（已执行 `a6301bd0`，15 处）。
剩下的 **20 处**是同一个颜色用在 `border` 上，D20 要求「单独报、不混进阴影表」。本条件即该裁定。

- **决策**：描边用途的 `rgba(57,45,26,α)` **归并到 `--sb-border-*`（暖黑系 `rgba(12,10,9,α)`）**，按 α 落档：

  | 原 α | 目标 | 值 |
  |---|---|---|
  | ≤ .08 | `--sb-border-subtle` | rgba(12,10,9,0.06) |
  | .09 – .12 | `--sb-border-default` | rgba(12,10,9,0.10) |
  | ≥ .13 | `--sb-border-strong` | rgba(12,10,9,0.16) |

- **依据**：**描边是「分区 / 边界」语义，全站只该有一套描边色**（D4 定的暖黑）。
  保留一支「暖棕描边」= 第二套边界语言 = 碎片化，与「品牌紫不补 550/650」是同一把尺。
  **阴影（海拔）与描边（边界）是两种用途 → 两个家族**；但不能有第三个。

- **口径要求（依 D20-D）**：报证据时必须用**合成到实际底色后**的 ΔE，不能用原始值。
  原始 ΔE 21.6 是**不透明色**的比较结果；而这批是 **α≈0.05–0.16 的发丝线**，
  叠加到暖米底（`#F5EFE4`）后，两者的实际呈现差异远小于 21.6 —— 这正是 D20-D 说的「alpha 值纯 RGB 比对失真」。

- **例外（单独报，不许自行归并）**：若某处描边位于**深色或暖棕底**上，换成暖黑后会**看不见** ——
  这类报我，不做机械归并。

- **性质**：**有意观感变更**（发丝线色相变化），必须附分区段像素 diff（D14）。

### 附：交互态基线（§22 / 原则 4.7）
本轮同时立了 **§22 交互态基线**：凡 `cursor: pointer` 的元素**必须有 `:hover`**，
且只改一个通道（中性底→`--sb-hover-bg`；实色底→`--sb-shadow-3`；卡片→海拔抬升）。
实测 **332 个**可点选择器里 **134 个没有 hover** —— 已下派批量治理。


## D18 · 圆角归并的「按场景」实操规则（2026-09-20）

- **背景**：D6 早就定了「圆角只有 20/16/12/8/6（+24 大容器 / 9999 胶囊）」，并写明 10px（62 处）

## D28 · V2 的 `--duration-fast`(120ms) 归并到 §14 的 `--sb-dur-fast`(150ms)—— **拒绝为它加档**（2026-09-15）

### 问题

V2 `--duration-fast: 0.12s`（120ms）**不在 §14 动效阶梯上**（instant 100 / fast 150 / normal 200 /
slow 300 / slower 400 全为 50 的倍数）。按 D15，非阶梯值要么**保持字面量**，要么**先加档**。
它却有 **30 处**真实使用（5 个文件），是剩余 V2 里最大的一块。

### 裁定：归并到 `--sb-dur-fast`(150ms)，**不加 120ms 档**

三条依据：

1. **120ms 不是行业标准档** —— Tailwind 的 duration 刻度是 75/100/150/200/300/500/700/1000，
   Material 是 100/200/300。**两者都没有 120**。
   依 **D16** 的判据（加档必须是「行业标准半档」，如 2/6/10px ↔ Tailwind 1.5/0.5/2.5），
   为 120ms 立档 = **把碎片化制度化**，与 D16 拒绝 1/3/5/7/9px 是同一把尺。
2. **角色对应** —— §14 的 `--sb-dur-fast` 定义原文是「**hover 位移**、图标旋转」；
   实测这 30 处**绝大多数含 `transform`**（位移），正是该档的角色。
   而 `--sb-dur-instant`(100ms) 的角色是「状态**色**变化：hover 文字/背景」——只覆盖其中一小部分。
3. **不硬套（D15）** —— 所以本条**明确定性为「有意观感变更（+30ms）」**，
   **不是**「逐值相等迁移」，必须单独裁定（本条即该裁定）。

### 证据（**计算样式 A/B**，浏览器实测）

| 表达式 | 改动前解析 | 改动后解析 |
|---|---|---|
| `var(--duration-fast)`（V2，定义仍在） | **0.12s** | — |
| `var(--sb-dur-fast)`（V3 阶梯） | — | **0.15s** |

> ⚠️ **为什么不用像素 diff**：时长是**时间维度**的属性，静态截图**不含时间信息**，
> 整屏 diff 对它**恒为 0**，会给出「无变化」的假证据。
> 这类变更的正确证据是 **computed style A/B** —— 逐表达式读
> `getComputedStyle(el).transitionDuration`，看它是否精确地从 0.12s 变成 0.15s。
> **推论（补进方法论）**：D14 的「分区段像素 diff」是**视觉属性**的判据；
> **非视觉属性（时长 / 缓动 / z-index / 层序）必须换判据**，否则等于没验。

### 保留项：`--duration-slow`(350ms) **不硬套**

实测同样确认了两者**不相等**（`var(--duration-slow)` = **0.35s**，`var(--sb-dur-slow)` = **0.3s**），
依 D15「阶梯里没有的值保持字面量」**本批不动**（3 处），留待单独裁定。

### 连带发现（登记，本批未处理）

页面实测有 **25 个 `<img>` 元素把 `transition: opacity 120ms` 写成了 JSX 内联字面量**，
与 V2 的 `--duration-fast` 是**同一个 120ms 值**的两条来源。
→ 也就是说 120ms 在本仓**确实被当成一个感知档在用**（只是没进阶梯）。
本裁定仍然成立（它不构成行业档、且这 25 处本身也是待收编的硬编码），
但**下一位若要为 120ms 立档，必须把这两条来源一起处理**，不能只处理其中一条。

## D29 · V2 超圆角档按 **D18 角色表逐处定档**，不压成单一档（2026-09-15，结清 D24 第 3 条）

### ⚠️ 登记：本批带出一个**额外的**变更（未单独验证）

| | V2 覆盖点 | V3 覆盖点 |
|---|---|---|
| 断点 | `@media (max-width: 768px)` | `@media (max-width: 640px)` |

| `--text-3xl` | ≤768 → **22px** | ≤640 → **24px**；≤1024 → **28px** |

### 方法论补充（与 D28 同族，继续累积）

> 「**用什么判据验**」由**该属性是否参与布局**决定，不能一律套像素 diff：
> · **不参与布局**（圆角 / 阴影 / 颜色 / 时长）→ 指纹 diff + 像素 diff 即可；
> · **参与布局**（字号 / 间距 / 尺寸）→ 必须量**几何**（注入式定量或整屏指纹的 w/h diff）；
> · **纯时间维度**（时长 / 缓动）→ 只能用 computed style。
> 三者混用会得到**看似通过、实则没验**的结论。

## D34 · DS 层债务 **hex 13 / rgba 27 / V2 3 → 0 / 0 / 0**；新增 §23「媒体之上」与 §24「阻断层」两族（2026-09-15）

### 四、关于「新增两个 token」的自我辩护

有人会说「这不是把 9 个遗留 token 又搬到 V3 了吗」。区别在于：
- **V2 的 9 个是「第二套语言」的成员** —— 它们与 V3 并存、同名可能不同值、且**没有单一权威**；
- **新增的两个是 V3 内部缺的角色**（反色面的 hover、随主题走的信息浅底），
  定义在**唯一权威文件**里、有命名理由、有注释说明它与相邻 token 的区别。
- 另 7 项是**真收敛**（值被改到 V3 阶梯上），不是搬运。
