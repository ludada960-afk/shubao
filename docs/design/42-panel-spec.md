# 面板规范（主次 / 间距 / 状态 / 不重复 / 分层）

> **建立时间**：2026-09-15 · **适用**：电商工作台与画布的**所有浮层面板**
> **唯一事实源**：`src/pages/Home/ec/panelVisualLanguage.js`（面板级） + `src/styles/design-tokens-v3.css`（token 级）

---

## 为什么会有这份文档

老板的原话（2026-09-15，六张批注图）：

> 「你做的东西都是一些有点像半成品的东西需要去调整，但实际上我要的是你自己已经有一套相关
>  的建立起相关的体系了，有一套这样的设计规范了，然后以后我们不管做什么东西不用我吩咐你，
>  你自己就知道要朝哪些方向去做。」

这份文档就是那套体系。**它不是参考读物，是判据清单**：每条规则都写明「判据 / 反例 / 谁在守它」。
违反任何一条，门禁会在提交前变红，不需要老板再讲一遍。

## R1 · 主次阶梯：控件值永远比它的字段标签更重

| 角色 | 字号 | 字重 | 墨色 | 用在哪 |
|---|---|---|---|---|
| groupTitle | 13 | 700 | --sb-ink-1 | 一组内容的名字（**必须带 14px 图标**，见 R9） |
| **value** | **13** | **600** | **--sb-text-primary** | **控件当前值（用户真正要读的）** |
| fieldLabel | 12 | 600 | --sb-ink-2 | 「这格叫什么」（**不许「素」**，见下方二次对齐） |
| helper | 11 | 400 | --sb-ink-3 | 描述 / 单位 / 提示 |

**判据**：`TEXT_ROLE.value.size > TEXT_ROLE.fieldLabel.size`，且 value 的墨色比 fieldLabel 深。
**反例**（真实发生过的 bug）：标签 12/600 比控件值 11/600 还大 → 两者同级，整片糊在一起。
**守它的门禁**：`test/workbench-panel-ux-0915.test.mjs` ⑦ ⑳

### 2026-09-15 二次对齐（返工记录，必读）

这张表原本写着 fieldLabel = 12，而 `TEXT_ROLE.fieldLabel` 实际是 **11** ——
**文档与代码互相打架**，上一轮我照着这份错文档以为已经统一，实际根本没改。
现在两处锁死同值（门禁 ⑳）。

同时把标签从 `11 / --sb-ink-3` 抬到 `12 / --sb-ink-2`：

- 用户批注图4-①：「你的这些小标题都太素了。就是太简单了，感觉就像个demo一样。」
- 用户批注图5-②：「避免出现的元素……他的标题等级没有对齐上面那四个标题的等级呀。
  就看起来他就非常的突兀啊，又大又加深，这些东西都跟他们不一样。」

后者的根因**不是那个标题太大，而是标签太小太浅** —— 落差被放大成了「参差不齐」。
两档现在只差 1px + 一个字重，层级靠**图标 + 间距**区分，不靠悬殊字号。

取样式用 `textRoleStyle('value')` / `textRoleStyle('fieldLabel')`，不要在面板里手写 size/weight/color。

## R2 · 间距阶梯：8pt，唯一允许的半档是 4px

| 档 | px | 用在哪 |
|---|---|---|
| sp1 | 4 | 图标 ↔ 文字（唯一半档） |
| sp2 | 8 | **字段标签 ↔ 它的控件**；相邻行（= `fieldStackStyle`） |
| sp3 | 12 | 控件 ↔ 控件；**分组标题 ↔ 它的内容** |
| sp4 | 16 | 分组 ↔ 分组 |
| sp5 | 20 | **面板左右内边距** |
| sp6 | 24 | **面板上下内边距** |

**六档必须用对关系**（2026-09-15 修正）：标签↔控件 8 < 控件↔控件 12 = 标题↔内容 12
< 分组↔分组 16 < 面板内边距 20 / 24。

**反例（真实 bug）**：共享常量 `sectionStyle` 的 gap 是 sp5(20)，却被当成
「字段标签 + 控件」的容器用了 5 处 —— 于是同一个面板里「品类 → 输入框」是 20px，
而紧挨着的「产品尺寸 → 输入框」是 8px。用户批注图5-③「品类与输入框间距过大」就是它。
该常量已**删除**，统一走 `fieldStackStyle`（sp2）。
**守它的门禁**：`workbench-panel-ux-0915` ③ ⑲ ㉑

**判据**：面板里不得出现 1px / 2px 这类「贴死」间距；相邻可选中的行之间必须 ≥ 8px，
否则两行的选中环会在视觉上贴成一条（用户批注图2-①：「紫色的边框已经完全重叠了」）。
**守它的门禁**：「技能库 CSS 不再出现 1px/2px 的贴死间距」+ `workbench-panel-ux-0915` ③

## R3 · 状态三通道：hover / selected / focus 必须长得不一样

- **selected**：品牌浅底 + 品牌描边 + ring（`--sb-shadow-ring`）；
- **hover**：只做底色（`--sb-state-hover-bg`），**不得**与 selected 同款；
- **focus-visible**：统一焦点环（`--sb-focus-ring`）；
- **边框宽度恒定**：状态变化只改底色/ring，不改 border-width（否则布局抖动）。

**反例**：用内联 style 在 `onMouseEnter` 里改样式 —— 会覆盖声明式伪类，于是 hover 与 selected 长得一样。
**守它的门禁**：`design-tokens-v3-adoption`（D2 ring + .sb-opt 预置类）

## R4 · 同一信息只渲染一处

**判据**：同一份数据不得在同一个视野里出现第二次。
**反例**（真实批注）：面板里写一遍「当前方案：淘宝 · 白底首图×1…」，而底部按钮已经实时显示同一份摘要
（用户原话：「下面的那个面板按钮它是会跟着显示跟着调整的……在这里是重复的功能」）。
另一个反例：分组大标题 + 每个控件的字段标签，是**同一层级信息写两遍**（用户批注图5-①）。
**守它的门禁**：`workbench-panel-ux-0915` ④⑨⑩ · `ecommerce-billing-ui`（套图摘要唯一渲染点）

## R5 · 图标只用项目图标族，禁止 emoji 当图标

**判据（分两档，别混用）**：

- **通用功能图标** → 用 `lucide-react`，尺寸一律取 `ICON_SIZE`（分组标题 14 / 字段标签 12 / 行内 12），
  不得在调用点写 `size={13}` 这种字面量；
- **有语义身份的类型图标**（图片类型那种「这是什么」）→ **必须自绘**：成套、共用底板、duotone
  （只用 `currentColor` + 透明度，自动跟随主题与选中态）。实现：`src/pages/Home/ec/ImageTypeGlyph.jsx`。
**反例**：emoji（⬜🖼️📱🔲📋）——形状与配色随系统字体变化，天然带「占位」观感
（用户原话：「完全就是那种很简单的那种 demo 版的东西」）。
另一类反例：**拿通用图标库的符号硬凑一套**（`Square` / `Scissors` / `Rows3` 摆在一起既不成套，
语义也对不上 ——「剪刀 ≠ 去底」）。
尺寸差同样是判据：类型徽章 36 必须是勾选框 16 的 2 倍以上（见 R6）。
**守它的门禁**：`workbench-panel-ux-0915` ⑤ ⑯

## R6 · 点击区：≥32px；整行可点时整行 ≥48px

- 勾选框这类**纯视觉指示器**不承担点击（点击由父行承担），因此可以小于 32px；
- 但**状态指示器与内容图标必须有大小差**：勾选框 **16** vs 类型徽章 **36**（≥ 2 倍）——
  两者同大时用户批注：「打钩的框怎么跟你的图标是一样大的呀？这样从视觉上看起来，他就又没有主次之分了」。

**⚠️ 这条返工过一次，教训写在这里**：初版锁的是 28 vs 18（1.56 倍），用户复核时
**仍然**说「怎么还是一模一样大」。所以判据从「写死两个数字」改成「**倍数 ≥ 2**」，
数字只在 `ICON_SIZE` 里定义一次。若下一轮还被说「一样大」，要改的是**形态**
（方形勾选框 vs 圆形状态点），不是继续放大尺寸 —— 继续放大会撞到 48px 行高上限。
**守它的门禁**：`home-panel-resizable-inputs` ④ · `workbench-panel-ux-0915` ⑥ ⑯

## R7 · 配色只用 token：不得硬编码，也不得用不随主题翻转的原色做底

**判据**：面板内不得出现裸 hex / rgba；控件的底必须用**会随主题翻转**的语义 token。
**反例**（真实 bug）：共享的 `inputStyle` 用了 `--sb-neutral-0` 做底 ——
那是品牌原色、**不随主题翻转**，于是暗色主题下这些输入框会变成白框；配一个硬编码冷灰边框，
整片就是老板说的「黑字白底极简风」（用户批注图5-①）。
**守它的门禁**：`workbench-panel-ux-0915` ⑫ · `design-tokens-v3-adoption` · `legacy-token-family`（棘轮）

## R8 · 分层：面板是保险丝，提示词是方向盘

这是**产品逻辑**，不是视觉细节，但它决定了前面七条怎么用：

| 层 | 回答什么 | 例子 | 谁优先 |
|---|---|---|---|
| **配置面板** | 机器必须精确知道的 | 张数 / 比例 / 材质 / 禁忌 / 平台合规 | **冲突时以此为准** |
| **提示词** | 人想表达的 | 画面 / 构图 / 情绪 / 文案 | 面板管不到的地方全归它 |

**落地要求（三条，缺一不可）**：
1. **只在真撞车时才说话** —— 没有冲突（含提示词为空）时该组件渲染 `null`，一个字都不出现；
2. 检测到冲突**当场**告诉用户「出图按哪边来」，并**点名用户能改的那一栏**，不要讲机制；
3. **不得静默替换**用户输入。

⚠️ 第 1 条**推翻了初版**：初版要求「常驻一句分工说明」，而实测中用户提示词为空、
只是点了个技能，那句话照样显示 —— 用户原话：「我提示词里面并没有写入任何东西啊，
为什么我只是在面板里点个技能它就会出来这个呢。」
**没冲突时用户不需要上课**；常驻说明等于在用户没提问的时候先回答一遍，反而像报错。

文案同理，用户原话：「你这个表达不够接地气呀，用户根本不知道这是什么意思，
你这句像是在对我交代的，根本不是对用户交代的呀。」
→ 对用户的提示语里不得出现「硬约束 / 权威性 / 越权 / 优先级」这类内部术语。

实现**复用既有判定**（`canvasPromptAuthority.detectHardConstraintConflicts` / `isStructuralIntent`），
不新造一套。呈现组件：`src/pages/Home/ec/PromptAuthorityNote.jsx`。
**守它的门禁**：`workbench-panel-ux-0915` ⑬⑭

## R9 · 标题与标签只有一个实现：`PanelPrimitives.jsx`

**判据**：面板里不得出现 ——

- 直接使用 `groupTitleStyle` 的散装标题；
- 局部定义的 `GroupTitle` / `FieldLabel`（无论叫什么名字都算）；
- 手写的字号 / 字重 / 颜色字面量。

只能 `import { GroupTitle, FieldLabel } from './PanelPrimitives.jsx'`，
且**分组标题必须带图标**（`icon` 必填、尺寸取 `ICON_SIZE.groupTitle`；
忘了传不会崩，但会退回「裸标题」那种参差长相，门禁 ⑮ 会红）。

**反例（2026-09-15 实测，四个来源同时存在，这正是用户看到的「参差不齐」）**：

1. 生成设置自己实现了一套 **10px / 灰** 的分组标题，而其它面板是 13/700/近黑；
2. 套图方案的「图片类型」是**裸的** 13/700、没有图标，而「避免出现的元素」有 ——
   同一档两种长相；
3. CopyPanel / SkuPanel 各自复制了一份 `GroupTitle`（删标题后已零调用）；
4. SkuPanel 的 `FieldLabel` 自写死 `12/600/ink-2`，与 `TEXT_ROLE` 是两份真相。

用户批注图6-⑧：「整个这下面所有的面板啊，他们的标题的设计方式好像都参差不齐的……
同一阶梯的东西，同一个维度的东西，那就应该把他们统一起来，同一套的设计语言。」

**守它的门禁**：`workbench-panel-ux-0915` ⑮ ⑳ ㉑

## 改面板的标准流程（照做即可）

1. 先读 `panelVisualLanguage.js` —— 你要的常量/阶梯十有八九已经在了；
2. 只在面板里**引用**常量，不要在面板里另写一份 size/color/gap（那就是「第二套真相」）；
3. 改完跑 `npm run precommit`（构建 + 21 条硬门禁）；
4. **改 UI 契约前必须再跑一次全量 `npm test`** —— precommit 只覆盖硬门禁的子集，
   历史上多次出现「precommit 全绿但部署被全量测试拦下」；
5. 用 pathspec 提交（`git commit -F <msg> -- <pathspec>`），不要 `git add -A`。

## 一条给未来的提醒：门禁必须先剥注释

本规范的多条门禁**都**要先剥注释再断言（复用 `scripts/lib/token-scope.mjs`）。
原因是这条教训在本仓库反复出现：解释「为什么删掉 X」的注释里必然会写到 X 的名字，
门禁若把注释算成用法，就是在**惩罚「把来龙去脉写清楚」**。
（同族事故：legacy-token-family 的假零、nano-model-single-source 的初版假阳性、本规范的 ⑤⑪。）
