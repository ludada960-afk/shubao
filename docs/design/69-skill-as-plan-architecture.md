# 69 · 技能＝方案（Skill as a Plan）：把「选模型」从子页面里拿掉

> 用户批注（2026-09-24，本项目最重要的一条方向性批评）：
> 「我之前就跟你说过这个问题啊，我说**可能不是模型问题**，知渔他们**也没有在数字人这些子页面里面给你选模型的权力**，
> 那选模型有可能也不是关键吧，你现在到底有没有做**深度的项目设计**呀，为什么思考方向那么单一降智呢」

这份文档就是那份"深度设计"。它不是又一个页面改动清单，而是**重排我们对"技能"的定义**。

---

## 一、现象：我们做的是"参数台"，知渔做的是"方案"

把两边的子页面摊开对比（实采数据：`docs/design/data/quantv-video-pages.json`）：

| | 知渔的子页面 | 我们的子页面（现状） |
|---|---|---|
| 用户要填什么 | **业务信息**：主题 / 文案类型 / 人设 / 产品 / 卖点 / 参考图 / 比例 | 业务信息 **＋ 模型 / 清晰度 / 时长** |
| 模型 | **不可选**（页面上根本没有这一格） | 每页都有一格「视频模型」 |
| 规格 | 少数页给"输出分辨率"（高清页）或"时长"（短剧页），其余由页面定 | 几乎每页都给「清晰度」「时长」 |
| 用户心智 | "我描述我的生意，平台给我成片" | "我是操作员，我来调参数" |

**这就是用户说的"选模型不是关键"的真正含义**：知渔的数字人 / 短剧 / 室内展示这些页面之所以能成立，
是因为**平台替用户决定了模型与规格**，用户只负责说他自己的生意。我们把决定权推回给用户，
结果就是：用户不知道该选什么、我们每条 skill 的差异被"模型/清晰度/时长"三格抹平（42 条视频 skill 里
41 条的字段就是同一个共享常量 `VIDEO_BASE_FIELDS`），**看起来全都一样** —— 这正是用户反复说的"每页都长得差不多"。

## 二、判断：技能＝方案，模型＝实现细节（本项目的架构原则）

```
技能（Skill）  =  一条能独立交付的【方案】：输入业务信息 → 输出成片
                     │
                     ├── 方案步骤（steps）：可多步（生成文案 → 配音 → 合成 → 交付）
                     ├── 默认规格（defaults）：比例 / 时长 / 清晰度（由方案定，不问用户）
                     └── 实现（routes）：由**路由层按能力选**，可替换、可降级
```

三条由此推出的结论：

1. **模型不进子页面的业务字段**。用户点进「数字人」是想做口播视频，不是想选 ai-video 的哪条路由。
   模型选择属于**实现层**：由方案的 `capability` 需求 + 路由台账（可达性/成本/余额）自动决定。
   保留入口的方式是**高级设置（默认折叠）**，而不是摊在主表单里 —— 这与知渔一致（他们连折叠都几乎没有）。
2. **规格由方案定，不由用户逐页调**。知渔的短剧页才给时长（因为时长是那个玩法的卖点），
   室内展示页连时长都不给。我们要改成：**默认值来自方案**，只有"这个玩法本身就需要用户选"的才露出来。
3. **能力≠单一模型**。用户上一轮的追问（"难道不是因为 skill 封装的方案吗"）在这里闭环：
   高清 / 去字幕 / 数字人 三件事都不必是"某个上游模型"，而是**方案**：
   | 能力 | 方案（steps） | 实现（可替换） |
   |---|---|---|
   | 视频高清 | 输入视频 → 提分辨率 → 交付 | **本地 ffmpeg scale**（已有渲染管线）→ 后补 Real-ESRGAN 增强；未来可换上游超分路由 |
   | 视频字幕去除 | 输入视频 →（手动框选 / 自动识别）字幕区域 → 区域擦除补全 → 交付 | **本地 ffmpeg delogo**（手动）；自动识别后补（OCR/视觉定位）|
   | 数字人 | 文案生成 → **TTS 配音（站内已有）** → 口型合成 → 交付 | 本地 Wav2Lip / SadTalker；未来可换上游唇形路由 |

   ⇒ **"上游有没有这条模型"不再是"能不能做"的判据**；判据是"这条方案能不能交付"。
   这解释了知渔的定价：视频高清 **0.50 积分**、去字幕 **0.04 积分/秒** —— 便宜到不可能是按上游模型计价，
   **他们大概率就是本地处理**。我们照抄他们的价格在上游路线上会亏，在本地路线上是赚的。

## 三、落地方案（怎么改，改哪里）

### 3.1 声明层：技能新增 `plan`（方案）字段

```js
// src/skills/videoSkills.js（示意）
{
  id: 'video.upscale', name: '视频高清',
  plan: {
    steps: ['ingest', 'upscale', 'deliver'],        // 方案步骤
    engine: 'local-render',                           // 本地渲染管线（非上游生成）
    defaults: { resolution: '1080p' },                // 规格由方案定
    userFields: ['resolution'],                       // 只暴露"输出分辨率"一格（照知渔）
    hideModel: true,                                  // 明确不给用户选模型
  },
  fields: [ /* 业务字段，不含 model */ ],
}
```

### 3.2 工作台层：`VIDEO_BASE_FIELDS` 从"每页都有"改成"按方案给"

- 现状：`VIDEO_BASE_FIELDS = [模型, 清晰度, 时长]` 被 41/42 条 skill 共享 —— 这就是"千页一面"的根。
- 目标：模型/清晰度/时长**默认不出现**，由方案的 `defaults` 决定；
  需要用户选的才在 `plan.userFields` 里逐个声明（例如短剧页只给时长与比例，高清页只给输出分辨率）。
- 兼容：`advanced: true` 的技能仍可在「高级设置」折叠区里保留模型选择（给专业用户，不打主流程）。

### 3.3 路由层：模型由能力需求选，不由用户选

沿用现有 `server/videoCatalog.mjs` 的路由台账 + `videoModelRouter.recommendVideoRoute`，
但触发点从"用户在面板里选"改成"方案按 capability + 扣费上限 + 余额可达性自动选"。
这正是路由台账存在的意义（可达性/成本/余额都是运行时事实）。

### 3.4 计费：按方案实际消耗

不变（我们已经是"方案分析 + 成片"两段计价）。本地方案（高清/去字幕）的**上游成本≈0**，
定价空间大 —— 但**改价仍需用户点头**（钱路铁律）。

## 四、落地顺序（按"能不能独立交付 × 依赖最少"排）

| 批次 | 内容 | 依赖 | 状态 |
|---|---|---|---|
| ① | **视频高清（本地）**：上传视频 + 输出分辨率，走 ffmpeg scale 渲染 | 已有渲染管线 | 下一步就做 |
| ② | **视频字幕去除（本地·手动框选）**：照知渔的"标记方式"字段 | ffmpeg delogo | 紧随其后 |
| ③ | **数字人（方案流水线）**：文案 → TTS（已有）→ 口型合成（本地） | Wav2Lip/SadTalker + CPU 算力评估 | 最后，涉及基础设施 |
| ④ | **全站收口**：把 41 条共享 `VIDEO_BASE_FIELDS` 的页面按 §3.2 改成"方案默认值 + 只露该露的" | ①②③ 的字段形态定了再统一改 | 收尾 |

## 五、这份设计要防的两件事（写下来，免得下次又跑偏）

1. **别再拿"上游有没有这条路"当"能不能做"的判据**。判据是**这条方案能不能交付**；
   上游只是实现之一，本地渲染/本地推理也是实现。
2. **别再把"实现细节"摊给用户**。用户只要说他的生意；模型、清晰度、时长由方案定。
   每次想把某个技术参数放进子页面之前，先问一句：**知渔那一页有这一格吗？**
