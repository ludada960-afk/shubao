# AI 视频 P0 可靠性根因审计

日期：2026-08-15

状态：只读审计完成；未实施新平台代码；未触发付费视频生成。

## 1. 审计目的

本审计回答长期 AI 视频路线进入实施前最重要的一个问题：现有薯包视频链路能否安全地承载项目、资产、分镜、候选和时间线。

结论是：现有链路已经有幂等创建、队列、公平调度、熔断、供应商任务追踪、启动恢复和钱包预授权等基础，但视频任务没有完整复用站内已经验证过的租约、交付检查点、资产版本和运营处置能力。直接在其上增加长视频节点会放大结果丢失、积分冻结、资产暴露和人工复核死锁。

P0 的目标不是承诺绝不失败，而是让每次失败都可检测、可恢复、可对账、可人工闭环，并且不重复付费提交。

## 2. 已证明的现有能力

### 2.1 视频任务与供应商执行

- `video_jobs` 对 `(owner_email, idempotency_key)` 建立唯一约束，同一用户的同一创建动作不会建立两条任务。
- 供应商提交前先写入 `submitting`；一旦取得 `provider_task_id`，重试和重启恢复只轮询既有任务，不重新提交。
- 队列支持总并发、路由并发、用户公平调度和路由熔断。
- 任务保存创建时的产品、供应商路由、目录版本和成本快照，历史账务不随现价漂移。
- 视频任务和报价的现有定向回归测试 39 项通过；未调用真实付费供应商。

### 2.2 站内已经存在但视频未充分复用的能力

- 钱包服务使用幂等预授权、结算和释放。
- `canvas_billed_action_claims` 已实现跨进程租约、租约续期、过期回收和 fencing token。
- 画布 one-shot 收费动作已验证“先保存 delivered 结果，再结算为 settled”，并覆盖跨进程 single-flight、租约回收和可恢复供应商任务。
- 项目系统已有不可变版本、`project_generation_runs`、恢复检查点、`project_assets`、作品/画布/合成引用保护和保留策略。

因此 P0 不应重新发明另一套泛化任务框架；应提炼上述已验证原语，建立视频专用的 `GenerationJob -> GenerationAttempt -> Delivery -> Settlement` 状态机。

## 3. 当前视频状态机

```text
queued
  -> submitting
      -> processing
          -> completed
          -> failed
      -> needs_review
```

当前实现把 `completed`、`failed`、`needs_review` 都视为终态。前端对 `needs_review` 停止轮询，服务端也没有重连、核验、释放、取消或管理员裁决接口。

这意味着 `needs_review` 不是“正在确认”，而是没有后续动作的死路。

## 4. 已证明的根因与故障窗口

### 4.1 P0-1：视频素材读取缺少所有权校验

证据：

- 上传 `/api/video/assets` 需要登录和视频权限。
- 读取 `GET /api/video/assets/:id` 不经过身份验证。
- `readAsset(id)` 仅按资产 ID 查询，不接收或校验所有者。
- 输入图片、输入视频、输入音频和输出视频都使用同一路由。
- 输入资产响应还设置了 `public, max-age=3600`。

影响：任何获得或猜中资产 URL 的第三方都能读取用户参考素材或结果。随机 UUID 降低枚举概率，但不是授权机制。

约束：不能简单给现有 GET 加登录后结束，因为供应商目前通过绝对公开 URL 拉取参考素材。正确方案必须分离两类访问：

1. 用户预览/下载：登录态 + owner/授权项目校验。
2. 供应商读取：短期、签名、单用途或受范围约束的 URL；或者由供应商适配器直接上传素材。

验收：跨账号和匿名读取返回 401/403；有效签名只在限定资产、期限和用途内可用；日志不记录签名密钥；缓存策略不把私有素材公开缓存。

### 4.2 P0-2：`needs_review` 无闭环

证据：

- 供应商提交响应未知或服务在 `submitting` 阶段重启时，任务进入 `needs_review`。
- `needs_review` 被服务端和前端视为最终状态。
- 视频 API 只有创建、列表和详情，没有取消、重试、重新核验、退款或裁决。
- 管理后台只把该状态统计为失败，没有操作入口。

影响：供应商可能已受理且仍在产生结果，用户却停止收到更新；预授权可能无限冻结；运营无法确认任务、接回结果或安全退款。

验收：每条复核任务都有 `review_reason`、最后一次提交证据、供应商请求指纹、预授权状态和下一步动作；系统可按供应商幂等/查询能力自动核验，无法自动核验时进入有 SLA 的运营队列；“确认已提交”“确认未提交并释放”“绑定已有供应商任务”“隔离争议”均写审计日志。

### 4.3 P0-3：失败释放异常被吞掉，但界面声称已退款

证据：

- `fail()` 对 `walletService.releaseItem()` 使用空 `catch`。
- 无论释放是否成功，任务都会写成 `failed`，错误文案固定为“冻结积分已退回”。
- 没有释放失败事件、修复队列或管理员处置动作。

影响：账务事实和用户文案可能不一致，冻结积分可永久占用。

验收：任务状态与账务状态分离；只有释放成功或幂等重放确认成功后才显示“已退回”；释放失败进入 durable compensation/outbox 并告警；重启后自动重放；后台可看到和处理超时冻结。

### 4.4 P0-4：交付、结算、任务完成和作品落库不原子

当前完成顺序：

1. 下载供应商结果并插入 `video_assets`。
2. 结算积分。
3. 更新 `video_jobs=completed`。
4. 写入 Works。

已证明的窗口：

- 文件 rename 后、资产行插入前崩溃：留下孤儿文件。
- 资产插入后、任务完成前崩溃：恢复时可能再次下载并建立第二个结果资产。
- 结算后、任务完成前崩溃：结算幂等避免重复扣费，但任务仍需可靠接回既有交付。
- 任务完成后、Works 写入前崩溃：启动恢复不会再处理 completed，作品永久缺失。

验收：

- 先写 durable `delivered` 检查点，保存输出 hash、大小、资产 ID 和供应商 attempt。
- 结算、任务终态和作品投影通过事务或 outbox 驱动，可重复重放。
- 输出资产按 `(attempt_id, content_hash)` 去重。
- completed 任务的 Works/项目投影缺失可由 reconciliation job 修复。

### 4.5 P0-5：视频资产是一次性孤岛

证据：

- `video_assets` 只保存 owner、kind、content type、bytes、file name 和时间。
- 不包含 project/version/run/attempt/role/content hash/代理文件/缩略图/授权/保留信息。
- 现有 `project_assets` 和保留服务不会保护或回收独立视频资产。

影响：无法追溯镜头引用的确切素材版本；无法安全克隆项目；无法判断哪些视频可清理；上传重复、输出重复和存储增长都不可治理。

验收：统一资产契约至少包含 owner、project、asset、version、run、attempt、role、content hash、原文件、代理视频、缩略图、媒体元数据、授权和保留状态；下游只引用固定版本。

### 4.6 P0-6：大文件上传和结果持久化整文件缓冲

证据：

- 浏览器直接用单个 POST 发送完整 File，没有进度、暂停、续传、分片、取消恢复或上传幂等键。
- 服务端在进入 `uploadAsset()` 前取得完整 Buffer。
- 多文件按每类串行上传；不同类型组并行。
- 供应商输出通过 `response.arrayBuffer()` 整体载入内存后再写盘。

影响：弱网大文件重试必须从零开始；页面不能准确展示进度；多个并发任务会产生内存峰值；上传完成前无法建立 durable upload session。

验收：本地 object URL 在解码后即时显示；云端上传不阻塞首次可见；大文件支持断点续传、校验和、取消与继续；服务端和供应商输出使用流式写入并有大小上限；代理转码和缩略图异步执行。

## 5. 测试缺口

现有测试能证明主流程、报价、幂等创建、恢复和供应商适配，但下列行为没有形成回归门：

- 匿名/跨账号不能读取视频素材。
- 供应商签名 URL 的范围、过期和重放。
- `needs_review` 自动核验、人工裁决和最终账务结果。
- 释放失败重放，以及文案不得提前声称已退款。
- 在 delivery、settlement、job completion、Works projection 每个边界注入崩溃后的恢复。
- 同一供应商结果重复回调/下载后的资产去重。
- 大文件断点续传、断网恢复和上传进度。
- 流式下载的大小限制、临时文件清理和进程重启。
- completed 任务缺失 Works/项目投影的对账修复。

## 6. 批准后实施顺序

本节是实施顺序，不代表已经完成。

1. **先补故障测试**：为上述六类根因建立可失败的路由、服务和故障注入测试。
2. **修复资产访问边界**：用户授权读取与供应商短期签名读取分离。
3. **引入 attempt/事件/补偿状态**：不迁移 UI 前先让旧 VideoStudio 使用新的 durable 状态机。
4. **闭环复核与退款**：自动核验、运营队列、审计动作、冻结超时监控。
5. **统一媒体资产**：版本、hash、代理、缩略图、保留和授权。
6. **接入断点续传与流式持久化**：优先评估 MIT 的 `tus-js-client`/tus 协议；服务端实现和存储需单独选型验证。
7. **生产迁移与对账**：双写、回填、校验、切读、回滚；不直接破坏旧 `video_assets/video_jobs`。

## 7. 进入 P1 的硬门槛

只有以下条件全部达成，才允许实现资产库、分镜和时间线：

- 资产读取通过 owner/授权项目校验，供应商读取使用受限凭据。
- 同一幂等动作在并发、重启、超时和未知提交结果下都不重复付费提交。
- 供应商成功结果在回调重复、下载中断和进程重启后可恢复。
- failed/needs_review/completed 的任务状态与真实账务状态一致。
- `needs_review` 有自动和人工闭环，且有处置 SLA。
- 大文件可续传，上传和结果下载不整文件占用进程内存。
- 任务、资产、作品和项目投影可对账并自动修复。
- 后台按供应商/模型/输入类型展示提交未知率、成功率、首帧时间、交付时间、重试率、冻结超时和每可交付秒成本。

## 8. 当前决策门

本审计没有绕过产品路线确认。推荐路线仍是路线 C：项目/资产/镜头优先的导演工作台；现有 VideoStudio 下沉为单镜头生成器。

产品确认路线 C 后，下一步应先写正式 P0 设计，覆盖数据库迁移、状态机、签名访问、故障补偿、前端状态、运营处置和回滚，再写逐文件实施计划并按测试驱动分批交付。
