# GPT Image 2 电商生成引擎设计规格

## 1. 目标

把现有“拼接参考图 + 长提示词 + 同步生成”的实现升级为结构化混合电商生成引擎，在不破坏现有前端流程和 `/api/generate-ecommerce` 兼容性的前提下，实现：

1. 商品主体、包装、Logo、颜色和 SKU 事实尽可能保持真实。
2. 设计方向贯穿整套图片，而不是只作为一段普通卖点文字。
3. 按平台、品类、素材质量和用户选择动态规划套图。
4. 生成任务可以异步执行、持久化、重试和进程重启恢复。
5. 使用真实质量门替代随机评分，并按失败原因最多自动修复两次。
6. 日常生产优先使用中转站成本最低的 `gpt-image-2` 与 `gpt-image-2-n`。
7. 生成尺寸与平台交付尺寸分离，最终文件由确定性后处理保证规格。
8. 电商生图改为按实际功能和成功交付结果计费；标准积分包的单笔贡献利润率不低于 70%，为服务器、人工、税务与售后预留约 10 个百分点，经营净利润率目标不低于 60%。
9. 建立不可篡改的积分流水、预授权冻结、成功结算、失败释放、退款和支付订单闭环。

## 2. 非目标

- 本轮不把整个 Express 服务一次性改造成微服务平台。
- 本轮不自动调用高价模型作为隐藏兜底。
- 本轮不承诺模型能够原生生成透明背景、完全准确的中文、认证内容或尺寸参数。
- 本轮不为每个平台和类目写死未经官方验证的永久规则。
- 本轮不重构与电商生成链路无关的页面和业务模块。
- 国内支付宝和微信支付未具备合规接入条件前，本轮只完成支付适配器、订单和前端状态，不展示可以实际付款的假入口。

## 3. 已确认的产品决策

- 采用结构化混合生成方案，而不是只修改提示词。
- 自动质检失败后最多进行两次定向修复；仍不合格时保留当前结果，展示失败原因并允许人工确认或重新生成。
- 商品事实与创意视觉分离：模型负责场景、光影、氛围和视觉语言，确定性程序负责需要绝对准确的数据与文字。
- 方向标题保持系统定义、只读；方向执行说明允许用户编辑。
- 默认先确认代表图，再批量扩展为套图，降低整套图片风格漂移和拼接感。

## 4. 当前实现必须解决的问题

1. 商品图和参考图在前端被压缩到最长边 800px、JPEG 0.7，包装文字、Logo 和材质细节在进入模型前已经丢失。
2. 多张输入被合成 Contact Sheet，再作为单张图发送；模型无法可靠理解每张图的独立职责。
3. 第二步设计方向只进入 `selling_points`，无法控制整套素材的色板、光线、构图和商业目标。
4. `customColors`、`sizing` 和部分分辨率设置虽然从前端发送，但生产路由没有真正消费。
5. 单图角色比例被全局比例覆盖，多种前端比例无法在后端生效。
6. 现有 2K/4K 尺寸存在边长、总像素和 16 倍数错误；失败后会静默回退到 1K。
7. “透明 PNG”、准确认证、检测报告、参数和 SKU 数量被交给模型自由生成，存在事实幻觉风险。
8. 质检函数使用随机分数，自动重生没有真实判断依据。
9. 同步请求等待时间长；上游 504 后任务可能仍在执行，但本系统无法继续追踪。
10. 上游结果 URL 约 24 小时过期，未及时转存会导致作品和画布图片失效。
11. 当前电商套餐按“套”扣一次，无法表达用户只生成一张、生成多张、局部重绘、4K 导出或智能分层等不同成本。
12. 现有支付接口信任前端提交的 `amount` 和 `sets`，用户可以篡改价格或购买额度；支付成功页和 webhook 也缺少完整的签名、订单状态与幂等入账闭环。
13. 小红书图文目前主要在前端把余额减 1，服务端余额没有形成可靠结算；刷新页面或绕过前端可能导致额度不一致。
14. Plog 两个入口都调用 `/api/plog-generate`，当前只做内测身份校验，没有服务端额度冻结与扣减，实际上没有完成按套收费闭环。

## 5. 总体架构

```text
原始商品图/参考图/用户配置
        │
        ▼
Asset Intake ── 原图存储、角色标注、基础质量检查
        │
        ├── Product Truth ── 商品事实、风险字段、人工确认
        └── Reference Style ── 色板、光影、构图、氛围
        │
        ▼
Campaign Bible ── 已选方向的结构化视觉规则
        │
        ▼
Asset Planner ── 平台、品类、素材与风险驱动的套图计划
        │
        ▼
Prompt Compiler ── 每张图独立提示词与输入图职责
        │
        ▼
Model Router + Async Provider Adapter
        │
        ▼
Quality Gate ── 规格、商品一致性、文字、平台和视觉质量
        │
        ├── 通过 ── Post Process / Export / Stable Asset Storage
        └── 不通过 ── Targeted Repair，最多两次
```

### 5.1 `ProductTruth`

商品识别必须使用独立 Schema，不能复用风格分析结果：

```js
{
  category,
  productName,
  silhouette,
  primaryColors,
  materials,
  components,
  packageText: [{ text, confidence, sourceAssetId }],
  logos: [{ description, sourceAssetId, bbox, confidence }],
  skuFacts: [{ name, value, source: 'user' | 'ocr' | 'vision' }],
  forbiddenMutations: [],
  uncertainFacts: [],
  sourceAssetIds: []
}
```

规则：

- `user` 来源优先级最高，OCR 次之，视觉推断最低。
- 低置信度尺寸、认证、成分、功效、数量和规格不能进入最终文案。
- `uncertainFacts` 必须在第二步明确展示，不得静默当作事实。
- Logo、包装正面、接口位置和结构轮廓写入 `forbiddenMutations`。

### 5.2 `CampaignBible`

第二步选中的设计方向编译为结构化规则：

```js
{
  directionId,
  title,
  editableBrief,
  commercialObjective,
  audience,
  visualKeywords,
  palette,
  lighting,
  composition,
  backgroundLanguage,
  typographyIntent,
  copyTone,
  consistencyLocks,
  prohibitedStyles,
  referenceAssetIds
}
```

每张套图必须引用同一个 `CampaignBible`，但可以根据图片角色改变构图和信息密度。

### 5.3 `PlatformPolicyRegistry`

平台规范以版本化数据注册表维护，每条规则包含来源和核验时间：

```js
{
  platform,
  categoryScope,
  role,
  recommendedCount,
  allowedRatios,
  exportSizes,
  maxFileBytes,
  formats,
  backgroundPolicy,
  textPolicy,
  requiredFacts,
  sourceUrl,
  verifiedAt,
  confidence
}
```

- 已核验的平台规则用于强校验。
- 登录后可见或随类目变化的规则以“建议值”展示，不冒充永久硬标准。
- 用户手动选择平台规格时，系统仍需校验模型尺寸合法性，再在导出阶段转换成平台尺寸。

### 5.4 `CategoryStrategy`

按品类提供策略，不写死最终画面：

- 服饰：版型、材质、上身效果、细节、尺码信息和搭配场景。
- 美妆：包装保真、质地、色号、使用方式、成分与功效事实保护。
- 食品：包装、净含量、口味、食用场景；禁止虚构认证与营养结论。
- 3C：接口、结构、尺寸、功能示意和参数表；参数必须来自用户数据。
- 家居：比例、材质、空间尺度、使用场景和细节工艺。

策略只决定“应该回答哪些购买疑虑”，不固定背景和模板，避免不同行业生成同一套图片。

### 5.5 `AssetPlan`

套图数量由平台、品类、用户选择和素材质量共同决定。每张计划包含：

```js
{
  id,
  role,
  purpose,
  ratio,
  generationSize,
  exportTargets,
  generationMode,
  productAssetIds,
  styleReferenceIds,
  requiredFacts,
  riskLevel,
  qualityChecks
}
```

默认智能方案遵循：

- 先生成一张代表图。
- 用户确认后再生成其余角色。
- 每张图独立生成；正式成片不使用九宫格。
- 长详情页拆为 5–8 个语义切片，分别处理购买疑虑，再统一色彩并拼接。
- `detail_slice_qc` 不再自动生成虚构证书；只有用户上传真实证明素材时才允许生成“品质背书图”。

## 6. 模型与清晰度路由

### 6.1 上游价格基线

根据 2026-07-25 中转站模型广场：

| 模型 | 1K | 2K | 4K | 本项目定位 |
|---|---:|---:|---:|---|
| `gpt-image-2` | $0.038 | $0.038 | $0.038 | 默认单图和高保真编辑 |
| `gpt-image-2-n` | $0.038 | $0.038 | $0.038 | 同风格批量 Agent 任务 |
| `gpt-image-2-auto` | $0.045 | $0.065 | $0.095 | 默认禁用 |
| `gpt-image-2-eco` | $0.100 | $0.100 | $0.100 | 默认禁用 |
| Gemini 3 Flash/Pro | $0.150–0.180 | $0.150–0.180 | $0.150–0.180 | 默认禁用 |
| `gpt-image-2-native` | 按图像输入输出计费且显著更高 | | | 仅显式高级模式 |

模型价格进入配置，不散落在业务代码；未来价格变化只更新 `ModelCatalog`。

### 6.2 默认路由策略

1. `gpt-image-2` 是默认模型：单张代表图、白底图、包装保真图、SKU 高风险图、局部修复和需要明确输入职责的编辑任务全部走它。
2. `gpt-image-2-n` 只用于已经确认 Campaign Bible 后的同风格批量任务，例如 2–4 张场景图或详情氛围切片。任务必须异步提交，不能阻塞 HTTP 请求。
3. `gpt-image-2-n` 出现超时、缺图、职责混淆或部分失败时，剩余角色拆成独立 `gpt-image-2` 任务，不重新生成已经合格的图片。
4. `gpt-image-2-auto`、`eco`、Gemini 和 `native` 不作为自动兜底，避免一次失败触发不可控成本。
5. `native` 只有在未来提供明确标价的“专业精修”选项且用户主动选择时才能调用。

### 6.3 清晰度策略

- 方向卡默认只展示结构化文字方案，不额外调用生图模型。只有用户主动要求视觉预览时才生成 1K 草案，草案不作为最终交付。
- 日常正式成片：2K。虽然中转价格与 1K 相同，但 2K 更适合包装、材质和平台二次裁切，是默认性价比最高的生产母版。
- 第一张代表图直接按 2K 正式母版生成，确认后继续扩展，避免先生成 1K 再重复付费重做同一张图。
- 4K：仅在用户选择大幅海报、长边高分辨率导出或最终精修时使用。当前 4K 属于超分，不能宣传为重新生成了更多真实细节。
- 平台交付尺寸由 Sharp 从合格母版确定性缩放、裁切、压缩和转码；模型不直接承担所有平台最终像素规格。

合法生成尺寸：

| 档位 | 方形 | 竖版 | 横版 | 竖屏 |
|---|---|---|---|---|
| 1K | 1024×1024 | 768×1024 | 1024×768 | — |
| 2K | 2048×2048 | 1536×2048 | 2048×1536 | 1152×2048 |
| 4K | 2880×2880 | 2448×3264 | 3264×2448 | 2160×3840 |

所有尺寸必须是 16 的倍数、总像素不超过 8,294,400、最大边不超过 3840、宽高比不超过 3:1。

### 6.4 并发与成本保护

- 中转站账户并发上限为 20；应用默认总并发设为 8，允许配置到 12，为后台任务和人工操作保留容量。
- `gpt-image-2-n` 默认并发 2，避免长任务占满通道。
- 同一作品最多并行生成 4 张，防止一位用户占满全局队列。
- 质检修复最多两次，且只修复失败图片。
- 内测账号 `867550189` 不受产品额度限制，但仍受并发、任务恢复和防重复提交保护，避免误操作造成无限并发。
- 服务记录每个任务的模型、尺寸、尝试次数、估算成本和最终状态。

### 6.5 中转站设置

- “只回 base64”保持关闭；保留 URL 返回并在收到结果后立即下载到本项目稳定资产存储，避免 Base64 放大响应和内存占用。
- 不依赖中转站“输出尺寸对齐请求”开关；本项目在 Provider Adapter 中校验实际尺寸并由后处理统一对齐。
- Provider Adapter 同时兼容 `Authorization: Bearer` 与现有 `x-api-key` 配置，但每个部署环境只能启用一种明确策略。

## 7. 多图输入与提示词编译

- 前端不再把商品原图压缩成 800px JPEG 后作为唯一输入；原图通过资产上传接口保存。
- 服务端生成轻量预览图供 UI 使用，原始资产用于视觉分析和图片编辑。
- 正式生成使用 `/v1/images/edits` multipart，多张图片按索引声明职责。
- 中转站最多接收 10 张编辑参考图，因此每张成片默认选择：
  - 1–5 张商品角度图；
  - 1–3 张高价值风格参考图；
  - 必要时 1 张包装或 Logo 保真图；
  - 总数不超过 10 张。
- Prompt Compiler 必须明确：`image[0]` 是主体、`image[1]` 是侧面结构、`image[n]` 仅借鉴光影或构图，不得复制其商品。
- 负面约束使用结构化风险规则，不堆砌“模糊、变形、多余手指”等通用词。

## 8. 高风险内容处理

| 内容 | 处理方式 |
|---|---|
| 场景、氛围、光影、材质表现 | 模型生成 |
| 商品轮廓、包装正面、Logo | 模型编辑 + 原图保护；必要时后期合成 |
| 中文标题、价格、促销、参数表 | 确定性排版 |
| SKU 名称、数量、尺寸、规格 | 用户数据驱动 |
| 认证、检测报告、功效与对比结论 | 仅使用用户提供的真实资料 |
| 透明 PNG | 生成后抠图与 Alpha 输出 |
| 长详情页 | 独立切片生成、统一色彩、确定性拼接 |

## 9. 真实质量门

质量门输出结构化结果，不再生成随机分数：

```js
{
  passed,
  checks: {
    technical: { passed, issues: [] },
    productFidelity: { passed, issues: [] },
    copyAndLogo: { passed, issues: [] },
    platformCompliance: { passed, issues: [] },
    visualQuality: { passed, issues: [] }
  },
  repairAction,
  confidence
}
```

- 技术检查：尺寸、格式、文件大小、透明度、损坏、白底和比例。
- 商品一致性：主体轮廓、主色、部件、包装和 Logo；第一版保留可替换评估接口，规则与视觉模型结合。
- 文字检查：OCR 对比用户提供文字，发现乱码、缺字和模型擅自添加文字。
- 平台合规：主图背景、文字、水印、边框和安全区。
- 视觉质量：模糊、噪点、过度锐化、色偏、主体截断和构图拥挤。

修复必须针对失败原因：

- 尺寸或格式失败直接后处理，不重新调用模型。
- 文字错误优先清除模型文字并确定性覆盖。
- 背景或局部瑕疵使用局部编辑。
- 商品结构或颜色漂移才重新生成该单图。
- 两次修复后仍失败，状态变为 `needs_review`，不无限重抽。

## 10. 异步任务与恢复

任务状态机：

```text
draft → queued → submitted → polling → downloading
      → quality_check → repairing → completed
      ↘ failed / needs_review / cancelled
```

数据库至少保存：

- 本地 job ID、上游 provider job ID、请求幂等键。
- 模型、尺寸、输入资产、Prompt 版本和 Campaign Bible 版本。
- 每张 Asset Plan 的独立状态、错误、重试次数和输出路径。
- 上游 URL、稳定本地 URL、文件哈希和元数据。

服务启动时必须调用恢复逻辑：

- `submitted/polling` 任务继续轮询上游。
- 已返回 URL 但未转存的任务继续下载。
- 已下载但未质检的任务继续质量检查。
- 同一幂等键不能重复扣费或创建重复任务。

## 11. API 兼容与迁移

- 保留现有 `/api/generate-ecommerce`，内部改为创建异步任务并返回 job ID；旧前端需要同步结果时通过兼容层轮询。
- 新增独立资产上传接口，逐步停止通过 30MB JSON Base64 传输大量原图。
- 现有作品和画布数据结构继续可读；新结果增加 `assetPlanId`、`directionId`、`campaignBibleId`、质量状态和稳定资产 URL。
- 模块化代码逐步接管生产路由，不一次性删除旧实现；通过 feature flag 和兼容测试切换。
- 数据库迁移必须可重复执行，并为旧任务提供默认值。

## 12. 错误处理与用户体验

- 请求创建成功后立即进入任务页，用户关闭页面不会中止后台任务。
- 任务按单张图显示进度，已完成图片即时可用，不等待整套图片全部完成。
- 429、网络错误和 5xx 使用有上限的指数退避；审核拒绝、无效参数和事实缺失不盲目重试。
- 上游任务超时但仍在执行时显示“后台生成中”，不能报成永久失败。
- 失败提示使用用户可理解的业务语言，并保留已通过的结果。
- 额度不足弹窗不得清空用户输入；充值或额度恢复后从原任务草稿继续。

## 13. 监控与稳定性

记录并展示：

- 队列长度、等待时间、各模型耗时和成功率。
- 上游 429/5xx/504、JSON 解析失败和审核拒绝。
- 每种角色的首轮通过率、平均修复次数和人工确认率。
- 生成成本、失败成本和每套有效交付成本。
- 进程重启次数、未恢复任务数、URL 转存失败数。

PM2 保持单实例或明确的共享队列模式，避免多个进程重复恢复并执行同一个任务。端口占用必须在部署前检查，避免再次出现 `EADDRINUSE` 重启循环。

## 18. 电商计费模型

### 18.1 计费原则

电商生图不再按“一个商品算一套”收费，改为统一的“AI 积分”模式：

- 用户只为实际选择并成功交付的 AI 能力付费。
- 同一批任务按每张成功图片或每次成功能力结算，部分失败只释放失败部分的冻结积分。
- 系统质检判定为不合格而触发的两次定向修复包含在原价格内，不重复扣费。
- 用户改变设计方向、文案或素材后主动重新生成，视为新的创作任务并重新计费。
- 裁剪、缩放、压缩、格式转换、详情切分、长图拼接和已生成文件下载等确定性本地操作免费。
- 用户在执行前能够看到本次预计消耗；后端最终价格只能来自服务端商品目录，不能相信前端传价。
- 价格与底层模型解耦。用户购买的是“2K 电商成片”“智能二创”等业务结果，不需要理解中转模型名称。

### 18.2 竞品中可借鉴的做法

已核验公开信息形成以下结论：

- 七牛拓图 AI：不同图像能力消耗不同积分；任务创建先冻结预计积分，成功后正式扣除。这一账务方式直接采用。
- Kyeo AI：提示词优化按最低额度预扣，实际消耗较低时返还，失败全额退回。采用“报价—冻结—实际结算—释放差额”。
- Van Gogh Studio：用户选择生成 1–8 张中的任意图片，只按选中的成功图片计费。采用按 Asset Plan 逐项结算。
- Photoroom：按成功处理的图片计费，不同能力具有不同权重；多种确定性编辑组合在一次处理内不重复收费。采用成功交付和功能权重设计。
- Pic Copilot：通过“不满意返币”降低用户对随机生成的风险感知。薯包不开放无条件主观退款，但系统质量门确认的明显失败自动返还积分。
- Pebblely：月度图片数量套餐简单，但未使用额度会过期，不适合上新节奏波动较大的国内中小卖家。因此电商积分包默认永久有效，不强迫用户按月清零。
- 椒图 AI、流影 AI 的公开页面能确认其按功能拆分产品，但没有可核验的公开金额；本设计不编造其价格。

### 18.3 用户可见功能价格

`1 AI 积分 = 1000 billing units`，数据库只存整数 billing units，支持 0.2、0.5 等小数积分而没有浮点误差。

| 功能 | 用户价格 | 结算单位 | 说明 |
|---|---:|---|---|
| 商品事实分析 + 4 个设计方向 | 0 | 每个素材指纹一次 | 作为首次生成获客成本；素材变化后重新分析仍免费，但受频率限制 |
| 1K 方向视觉草案 | 1 积分 | 每张成功图片 | 仅用户主动要求视觉预览时生成 |
| 2K 正式电商成片 | 1 积分 | 每张成功图片 | 主图、场景图、详情切片、SKU 创意底图统一计价 |
| 4K 正式成片或 4K 精修导出 | 2 积分 | 每张成功图片 | 4K 为高价值交付，不宣传为额外真实细节 |
| 智能二创 / 完整重绘 | 1 积分 | 每张 2K 成功图片 | 引用图片、反推提示词和补充素材后重新生成 |
| 局部 AI 重绘 / 文字区域清理 | 1 积分 | 每次成功编辑 | 底层仍需一次完整图片编辑调用，不能按“改动面积”低估成本 |
| 反推提示词 | 0.2 积分 | 每张外部导入图 | 薯包自己生成的图片首次反推免费 |
| AI 去背 / 透明 PNG | 0.5 积分 | 每张外部导入图 | 薯包生成结果首次去背免费；本地裁切和转码免费 |
| AI 画质增强 | 1 积分 | 每张成功图片 | 不等同于 4K 生成；显示实际输出尺寸 |
| 图片文字翻译与重排 | 0.5 积分 | 每张成功图片 | 文本识别、翻译和确定性覆盖合为一次能力 |
| PSD 智能分层 | 3 积分起 | 每张成功文件 | 只有真实分层服务接入并通过成本门禁后开放 |
| 裁剪、改尺寸、切图、拼长图、压缩、转格式、下载 | 0 | 每次 | 本地确定性处理免费 |

补充规则：

- `gpt-image-2-n` 批量生成仍按每张成功交付图扣积分，不按底层一次请求收费，用户无需承担缺图或部分失败。
- 智能套图按钮实时显示“计划生成 N 张，预计 N 积分”；用户增删图片角色后报价同步变化。
- 4K、PSD 分层等高成本功能显示积分标签和交付差异，不能用模糊的“高清品质”诱导升级。
- `PSD 智能分层` 的 3 积分是发布下限；若真实 Provider Adapter 报价无法满足 70% 单笔贡献利润门禁，该功能保持不可购买状态，而不是亏损上线。

## 19. 利润模型与积分包

### 19.1 标准 2K 图片的保守成本

中转站按人民币与美元数值 1:1 扣费，`gpt-image-2` 和 `gpt-image-2-n` 当前均为 0.038/次。标准 2K 图片采用以下保守成本预算：

| 成本项 | 单张预算（人民币） |
|---|---:|
| 图片模型调用 | 0.0380 |
| 自动修复成本准备金（按 30% 首轮失败率摊销） | 0.0114 |
| 商品分析和方向生成摊销 | 0.0060 |
| 资产存储、流量和图片后处理 | 0.0040 |
| 监控、队列和任务恢复 | 0.0040 |
| 欺诈、退款与异常成本准备金 | 0.0060 |
| 预估总变动成本 | 0.0694 |

支付通道费按收入的 3% 预留。先计算单笔贡献利润率：

```text
贡献利润率 = (实收金额 - 支付费 - 模型/分析/存储/重试等变动成本) / 实收金额
```

为使最终经营净利润率有机会稳定在 60% 以上，单笔贡献利润率门槛设为 70%，再预留约 10 个百分点覆盖固定服务器、人工、税务和售后。单个积分的最低实收价格约为：

```text
0.0694 / (1 - 0.70 - 0.03) = 0.2570 元
```

因此任何常规销售积分包都不能低于约 0.26 元/积分。系统使用 0.26 元作为当前成本门禁下限，并由运营配置保留上调空间。这里的 60% 是经营目标，不是仅扣模型费后的营销数字；上线后必须用真实固定成本和税费继续校准。

### 19.2 推荐电商积分包

| 积分包 | 价格 | AI 积分 | 单积分价格 | 预计标准 2K 图片 | 贡献利润率 | 扣除 10pp 经营准备金后的目标净利率 |
|---|---:|---:|---:|---:|---:|---:|
| 试用包 | ¥9.9 | 30 | ¥0.3300 | 30 张 | 约 76% | 约 66% |
| 上新包 | ¥29 | 105 | ¥0.2762 | 105 张 | 约 72% | 约 62% |
| 经营包 | ¥79 | 295 | ¥0.2678 | 295 张 | 约 71% | 约 61% |
| 工作室包 | ¥199 | 760 | ¥0.2618 | 760 张 | 约 70% | 约 60% |

- 电商积分永久有效，不按月清零。
- 价格页使用“约可生成 N 张 2K 成片”解释价值，同时明确 4K 和高级能力消耗更多积分。
- 暂不上架比 ¥199 更大的自助包，先根据真实重试率、存储和人工退款数据校准成本；大客户采用人工报价和独立毛利审核。
- 赠送积分与充值积分使用不同余额桶。退款只按未消耗的充值积分计算，赠送积分不可折现。
- 符合风控条件的新用户赠送 1 个限时电商积分，只能生成一张 2K 体验图；替换现有“免费体验一整套”的高成本承诺。赠送积分 7 天后到期，并限制设备、账号和请求频率。
- 小红书图文与 Plog 的现有价格和“套”概念保持不变，但底层迁移到安全账本；小红书/Plog 套餐额度与电商 AI 积分是两种独立货币，不能混扣。

### 19.3 动态利润门禁

`BillingCatalog` 为每个可收费能力保存：

```js
{
  sku,
  displayName,
  billingCurrency: 'ec_points',
  chargeUnits,
  providerCostCny,
  retryReserveRate,
  infraCostCny,
  targetContributionMarginRate: 0.70,
  targetOperatingNetMarginRate: 0.60,
  enabled,
  version,
  effectiveAt
}
```

- 发布或更新价格时自动计算最差积分包下的利润率。
- 单笔贡献利润率低于 70% 时后台拒绝启用该 SKU。
- 价格和上游成本按版本记录，历史订单永远使用创建时的报价快照。
- 每周根据真实首轮通过率、修复率、Provider 费用和退款率生成毛利报告；不自动改用户价格，由管理员确认后发布新版本。

## 20. 账务与数据库架构

现有 `users.credits` 不能继续作为唯一账本。新增：

### 20.1 钱包与流水

- `wallets`：用户、货币类型、可用余额、冻结余额和版本号。
- `wallet_ledger`：每一笔购买、赠送、冻结、结算、释放、退款和人工调整；记录前后余额、业务对象与幂等键。
- `credit_lots`：区分充值积分、赠送积分、来源订单和退款资格，消费时优先使用即将到期的赠送积分，再使用永久充值积分。
- `billing_holds`：任务创建时冻结的预计积分，可逐项结算或释放。
- `usage_events`：记录具体功能、图片、模型、尺寸、成本和质量结果。

余额不能直接覆盖，只能通过账本事务变更。每个业务事件使用唯一幂等键，重复 webhook、页面刷新和任务恢复不能重复入账或扣费。

### 20.2 报价、冻结与结算

```text
用户点击收费动作
  → POST /api/billing/quote
  → 服务端按当前配置和 Asset Plan 返回报价
  → POST /api/billing/holds（原子校验并冻结）
  → 创建生成/编辑任务
  → 每个输出成功：从冻结余额结算
  → 每个输出失败：释放对应冻结余额
  → 任务结束：释放未使用差额
```

- 报价包含 `quoteId`、版本、有效期、逐项费用和总积分。
- 冻结与任务创建在同一个数据库事务或可靠补偿流程中完成。
- 上游尚未提交前取消任务，全额释放。
- 上游已提交后用户可以停止后续图片，但当前进行中的图片继续完成；只有成功交付才结算。
- 系统自动修复使用原 hold 中的质量准备金，不向用户追加报价。

### 20.3 内测无限账号

账号 `867550189` 保持 `unlimited`：

- 不校验可用余额，不产生真实扣减。
- 仍创建 `usage_events` 和 shadow ledger，记录如果是普通用户本应消耗的积分与真实成本。
- 仍受全局并发、幂等和防重复提交限制。
- 管理后台能够单独查看内测成本，避免“无限额度”掩盖模型费用异常。

## 21. 付费拦截与交互闭环

### 21.1 动作前报价

- 所有收费按钮在可确定数量时直接显示价格，例如“生成 8 张 · 8 积分”“4K 导出 · 2 积分”。
- 套图配置修改、SKU 数量变化和分辨率变化后，价格实时更新。
- 用户点击前不需要反复弹确认框；首次收费或单次超过可配置阈值时显示确认，其余直接开始并显示已冻结积分。
- 方向标题、方案编辑、提示词编辑、素材管理和免费的画布操作不能被付费墙打断。

### 21.2 余额不足弹窗

弹窗必须展示：

- 当前动作名称和预计积分。
- 当前可用积分与还差多少。
- 推荐积分包及“约可继续生成多少张”。
- “当前商品图、设计方向、选择和提示词均已保存”的明确说明。
- 支付通道未开放时显示“支付通道筹备中，可联系管理员申请内测积分”，不显示可点击的支付宝/微信假按钮。

弹窗关闭后停留在原步骤。充值或管理员发放积分到账后：

1. 前端通过轮询或 SSE 更新余额。
2. 使用保存的 `pendingActionId` 重新获取报价。
3. 用户点击“继续刚才的生成”，从原状态继续。
4. 不跳回首页，不清空上传图片、方向、SKU、比例或文字输入。

### 21.3 质量退款

- 后端 Quality Gate 判定最终状态为 `failed` 时自动释放对应积分。
- `needs_review` 默认不结算，用户选择“接受当前结果”后结算；选择放弃则释放。
- 用户可以对明显商品变形、包装错误、空白图等提交“结果有问题”。系统复核通过后原路退积分，并记录失败标签用于质量报表。
- 主观更换风格、重新构图或改变要求不属于质量退款。

## 22. 支付订单与适配器

### 22.1 当前阶段

- 支付宝、微信入口使用 feature flag 关闭。
- 保留支付适配接口和接入文档，但前端不能声称“由 Stripe 支持支付宝/微信”或允许创建不可完成的订单。
- 内测阶段通过管理员后台发放积分或一次性兑换码完成充值验证；所有发放都进入账本并记录操作人、原因和审计信息。

### 22.2 正式支付架构

前端只提交后端定义的 `productSku`，不得提交可信价格或积分数量。服务端根据商品目录创建：

```js
{
  orderId,
  userId,
  productSku,
  amountCny,
  grantCurrency,
  grantAmount,
  provider,
  providerOrderId,
  status: 'created' | 'pending' | 'paid' | 'credited' | 'expired' | 'cancelled' | 'refunded',
  idempotencyKey,
  catalogVersion
}
```

- Provider Adapter 统一实现 `createOrder`、`verifyWebhook`、`queryOrder` 和 `refund`。
- webhook 必须先验证签名，再用 provider event ID 幂等处理。
- `paid → credited` 与积分入账在一个事务内完成；重复回调不重复加积分。
- 支付成功页只查询订单状态，不能直接加积分。
- 订单金额、商品名称和赠送积分完全来自后端目录快照。
- 支付失败、取消或超时不能影响用户当前创作草稿。

## 23. 计费测试与验收

### 单元测试

- 每个功能 SKU 的积分权重和利润率门禁。
- 0.2/0.5 积分使用整数 billing units 精确结算。
- 报价过期、目录版本变化和重新报价。
- 余额冻结、部分成功结算、失败释放和差额释放。
- 系统自动修复不重复扣费，用户主动重生成重新收费。
- 充值积分、赠送积分的消费顺序和退款资格。
- 内测无限账号不扣余额但生成 shadow usage。

### 安全与集成测试

- 修改前端 `amount`、`sets` 或积分数量无法改变真实订单。
- 重放 success URL、webhook 和任务回调不会重复加积分或扣积分。
- 并发创建两个任务时不能透支余额。
- 任务创建失败、上游拒绝和服务重启后 hold 能正确恢复或释放。
- 部分套图成功只扣成功部分。
- 支付通道关闭时接口和 UI 均返回明确的“暂未开放”，没有假支付入口。

### UI 验收

- 每个收费动作执行前能看到准确积分。
- 余额不足弹窗不改变任何当前输入和选中状态。
- 积分到账后可以继续原动作。
- 账单页能按购买、赠送、生成、编辑、退款和释放查看明细。
- 用户能理解 1 积分约等于一张 2K 正式电商图，但高级功能会显示不同消耗。

## 24. 计费完成标准

- 电商价格页不再出现“每套 N 张、消耗一套”的计价方式。
- 小红书套餐保持原定价和产品表达，底层账本安全迁移。
- 后端不再信任前端提交的支付金额和额度数量。
- 所有电商收费能力都通过版本化 Billing Catalog 报价。
- 任务在执行前冻结积分，成功后结算，失败后释放。
- 标准积分包在当前保守成本模型下单笔贡献利润率不低于 70%，并以覆盖固定经营成本后的净利润率不低于 60% 为运营目标。
- 内测无限账号可持续测试且能查看 shadow cost。
- 未备案阶段支付宝、微信保持关闭，但订单、Provider Adapter 和恢复原操作闭环已完成。
- 生产验收覆盖购买/发放、余额不足、继续原任务、部分失败退款、重复回调和并发防透支。

## 25. 小红书图文与 Plog 计费闭环

### 25.1 保持不变的产品价格

小红书图文继续沿用当前套餐金额和数量：

| 套餐 | 价格 | 完整创作套数 | 单套约价 | 单张重生成额度/套 |
|---|---:|---:|---:|---:|
| 入门 | ¥19 | 3 | ¥6.3 | 5 次 |
| 进阶 | ¥49 | 10 | ¥4.9 | 8 次 |
| 创作者 | ¥99 | 25 | ¥4.0 | 15 次 |
| 工作室 | ¥199 | 60 | ¥3.3 | 30 次 |

`1 content_set` 的交付定义：

- 小红书种草图文：完整标题、正文、标签、1 张封面和 8 张内容图。
- Plog：完整情绪文案、1 张封面和 8 张生活碎片图。
- 两种模式共用 `content_sets` 余额，因为对用户都属于一次完整的小红书内容创作。
- 电商生图使用 `ec_points`，两种货币完全隔离。

当前页面同时存在“月度套餐”和“套餐不过期”的冲突表达。首版按页面主逻辑统一为购买后 30 天有效的月度创作额度，额度到期时间在购买前明确展示；不自动续费。若未来改成永久包，只调整服务端商品目录的 `validityPolicy`，不改变账本结构。

### 25.2 服务端结算

小红书和 Plog 都必须使用与电商相同的报价、冻结和账本系统：

```text
开始完整生成
  → 冻结 1 content_set
  → 生成文案与 9 张图
  → 完整交付：结算 1 content_set，并创建该作品的重生成权益
  → 未达完整交付：自动补图；最终仍失败则释放 1 content_set
```

- 前端不再直接执行 `credits - 1` 作为真实扣费。
- `/api/generate` 与 `/api/plog-generate` 在任务开始前由服务端原子冻结额度。
- 两个 Plog 页面入口必须调用同一个账务服务，避免一个入口扣费、另一个入口免费。
- 用户刷新、关闭页面或切换模块不会取消后台任务；任务完成后仍能结算并保存作品。
- 同一 `generationId` 重放请求只返回原任务，不重复冻结或生成。
- 内测无限账号不扣 `content_sets`，但记录 shadow set、图片调用次数和真实成本。

### 25.3 完整交付与部分失败

- “完整一套”必须达到对应的文案字段和 9 张有效图片，不能只返回封面就结算一套。
- 单图失败先在任务内部定向补图，不消耗用户重生成权益。
- 自动补图后仍少于 9 张时，任务状态为 `needs_review`，默认不结算。
- 用户选择接受部分结果后才结算 1 套，并明确显示缺少的图片；选择放弃则释放冻结额度。
- 所有临时图片 URL 必须转存为稳定作品资产后，才允许任务进入 `completed` 并结算。

### 25.4 单张重生成权益

每个已结算作品创建独立的 `work_regeneration_entitlement`：

```js
{
  workId,
  sourceOrderItemId,
  includedCount,
  usedCount,
  remainingCount,
  expiresAt,
  planSnapshot
}
```

- 当前套餐中的 5/8/15/30 次表示每套作品可用的单张主动重生成次数。
- 系统错误、空白图、严重商品变形和审核失败导致的自动修复不占用次数。
- 用户主动更换画面、风格、提示词或内容时消耗 1 次。
- 重生成开始时冻结 1 次权益，成功后结算，失败后释放。
- 权益跟随作品，不允许在不同作品间挪用，防止高额度套餐被集中滥用于一个任务。
- 作品删除进入回收站时权益保留；永久删除作品时权益一并关闭，但不退还已购买套餐。

### 25.5 免费预览与新用户试用

- 匿名预览只允许生成文案和低成本封面预览，不生成完整 9 张高清图。
- 符合风控条件的新登录用户获得 1 个赠送 `content_set`，可完整体验小红书或 Plog 二选一。
- 赠送额度 7 天有效、不可退款、不与电商赠送积分互换。
- 免费体验也通过服务端账本结算，不能依赖 localStorage 的 `trialRemaining`。
- 同一设备、账号和异常网络环境受防刷限制；风控拒绝时保留用户输入并解释原因。

### 25.6 余额不足与恢复

- 小红书和 Plog 的付费墙显示“需要 1 套创作额度”，不能显示电商 AI 积分。
- 当前主题、正文、参考图、Plog 风格、排版和封面选择全部保存在草稿或任务快照中。
- 管理员发放或未来支付到账后，用户点击“继续刚才的创作”重新校验报价并启动原动作。
- 充值后不跳首页，也不要求重新上传参考图。

### 25.7 小红书/Plog 验收标准

- `/api/generate` 和 `/api/plog-generate` 均在服务端冻结、结算或释放 `content_sets`。
- 前端修改本地余额、直接请求 API 或重复提交不能免费生成或重复扣费。
- 小红书与 Plog 任一模式完整成功后扣 1 套；少图或失败默认不扣。
- 每套作品获得与购买套餐快照一致的单张重生成权益。
- 自动质量修复不消耗重生成次数，用户主动修改才消耗。
- 两个 Plog 入口的扣费、作品保存和失败处理行为完全一致。
- 匿名预览、新用户赠送、正式套餐和无限内测账号都有可审计流水。
- 现有套餐金额、套数和单套价格不改变，页面中不再同时出现“月度”和“永不过期”的矛盾文案。
