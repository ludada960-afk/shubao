①P0 图片性能：根因量化与修复结果

用户可感知问题：首页四模式入口卡首次加载慢、重复访问仍全量重下。

根因（三条，全部实证）

裸原图直出

四模式入口卡是 <img loading=eager> 直拉 210–332KB PNG 原图，合计 ~1153KB，且无内在尺寸（触发布局抖动）。

showcase 变体绕过缩略

ResponsiveImage 的 showcase card 变体绕过 .thumbs 目录，直取数 MB 源 PNG。

静态资源零缓存

express.static 对 /images、/assets 一律 max-age=0——每次访问全量重下。

配套加载策略与缓存分级

  • 模式卡改载 .thumbs WebP，声明 width=420 height=360 内在尺寸消除 CLS；decoding=async；默认卡 fetchpriority=high；index.html 预加载首屏缩略（6d54555）。
  • express.static 分级缓存：/assets immutable 1 年；/images、/gallery 7 天 ＋ stale-while-revalidate；/ 保持 no-store（686c833）。
  • 幂等缩略管线入库为 npm run images:thumbs，默认仅处理 src 引用图，--all/--force 可选（4fc4de9）。

③生图稳定性：七个失败点与修复（e73d9f8 / c2639b8）

电商生图链路（providerAdapter / nanoBananaProviderAdapter / orchestrator / 前端 generationStatusModel）通宵审计出的七类失败模式，一次收口；回归覆盖由独立测试提交保证。

#失败点（修复前行为）后果修复机制
1上游瞬时故障（网络抖动 / 5xx）一次即整单失败用户被迫手动重试submit 阶段指数退避自动重试（≤3 次），尊重 Retry-After 头
2上游繁忙（429/busy）被吞成通用错误无法判断能否重试重试耗尽后如实上报「上游忙」，标记 retryable 供前端引导
3提交请求悬挂（多模态图片上传时上游不响应）无限占用生成槽位显式 submit 截止 120s（AbortController 中断），超时归一为可重试 PROVIDER_NETWORK_ERROR
4轮询 GET 悬挂任务卡死在等待poll 截止 20s，超时可重试、不占槽位
5上游长时间不出结果停在中间态无解释POLL_TIMEOUT 独立语义，如实透出到状态模型
6进程重启或后台重试耗尽后，queued / analyzing / generating 任务无人接管任务永无终态、积分悬置启动恢复新增 sweepIntervalMs 周期巡检，持续接管卡死任务直至终态
7所有失败统一显示「视觉服务暂时不可用」真实原因被掩盖（如欠费）状态模型如实分类：AI 积分不足（含需/有余额）、费用确认过期、部分交付已计费说明、忙碌可重试
  1. e73d9f8 为实现提交（7 文件，+324/-25）；c2639b8 为对应回归提交（6 文件，+159 行）：backoff、deadlines、queued recovery sweep、truthful failure reasons 四组用例分别落在 api-error / canvas-generation-status / ecommerce-job-store / provider-adapter / startup-recovery-sweep 测试中。

3. /api/proxy-image 无鉴权 P1 加固项

4. 前端轮询上限交接 P2 体验项

pollEcommerceTask 默认 pollLimit=600 次（@1.5s ≈ 15 分钟）。超限后前端停止，而服务端任务可能仍在跑；当前依赖 e73d9f8 的服务端 sweep 兜底终态。建议补超限文案与「回作品页恢复」入口。
